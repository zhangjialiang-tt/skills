评审结论
这份 doc-code-align v1.0.0 的方向是正确的，但我认为它目前更像一个文档清理与代码一致性审计 Skill，还不是完整的“防止 AI Agent 长任务中文档膨胀与漂移”的解决方案。
建议修改后使用
它已经建立了几条有价值的纪律：

- 不凭模型记忆编写技术事实，必须追溯代码证据。
- 不以搜索片段代替完整的上下文分析。
- 区分历史记录与仍然有效的设计契约。
- 删除、修改、补充都要求有裁定依据。
- 对冻结文档及大幅删除设置人工确认门槛。
  尤其是“清理 ≠ 简化”这条应该保留，它能够防止 Agent 把重要的时序约束、边界条件和设计理由当成冗余信息删除。

不过，从实际工程使用角度，我发现了 3 个核心设计问题和 5 个实施层面的问题。
一、三个核心设计问题

1. “代码是唯一事实源”过于绝对
   原文：
   对技术文档执行「以代码为唯一事实源」的清理。

这在维护当前实现说明时通常合理，但并不适合所有技术文档。

例如 FPGA 项目中的寄存器接口：

- 需求规定 start 寄存器为写 1 触发。
- 当前 RTL 实际实现为电平保持。
- 文档正确描述了需求，但与代码不一致。
  按照现有 Skill 的规则，Agent 会把文档修改成“电平保持”，甚至删除原本正确的接口契约。

这实际上可能是用代码缺陷覆盖正确的设计需求。

应当明确区分三种事实：
事实类别 权威依据 处理原则
目标契约（Should-be） 冻结需求、接口协议、已批准架构决策 不允许被代码自动覆盖
实现事实（As-built） 当前代码、实际配置、依赖实现 用来核对当前实现状态
验证事实（Verified） 仿真、形式验证、板测证据 用来证明实现是否满足预期

建议将“代码是唯一事实源”调整为：

代码是当前实现行为的主要事实源，但不是需求正确性、设计意图和验证结论的唯一权威来源。

对于 doc-code-align，默认处理 As-built 文档。发现 Should-be 与 As-built 冲突时，必须标记，而不是静默修改需求。2. 缺少对“文档膨胀产生机制”的控制
这是我认为最重要的缺失。

目前 Skill 的五阶段工作流是：
已有文档

完整读取 → 事实核对 → 重写
清理后的文档

这可以清理已经膨胀的文档，却没有解决 Agent 为什么不断制造膨胀。

典型过程是：

第一轮设计产生架构方案，第二轮加入修正意见，第三轮增加验收条件，第四轮又记录例外情况。Agent 习惯追加内容，而不是替换已失效内容。

最终文档可能同时包含五个阶段的不同设计口径。

我建议增加一个文档更新策略：
当前有效契约

覆盖更新，保持单一口径

决策记录

必要时独立保存，禁止混入正文

进度记录

使用任务状态文件，完成后归档或清理

验证证据

单独存放，只引用关键结论

逻辑分离即可，不要求每种内容都创建独立文件。

核心约束是：

每一项有效设计事实，在其权威文档中只能存在一个可维护的定义位置。后续变更优先原位更新，不得通过不断追加历史说明形成多个口径。

这比事后清理更加有效。3. “全面重写”容易制造新的漂移
原文要求：
全文统一现在时契约口吻。

结构：契约优先（接口表/状态定义/流程），实现注记随后，理由性说明最后。

虽然目标是统一文档，但这一规则可能导致 Agent 在清理几个过期段落时，顺便调整整个文档的章节结构和表达。

结果是：

- Git diff 大幅增加。
- 无关段落被重新措辞。
- 原本准确的细节可能被概括掉。
- 人工难以审查哪些内容真正发生了变化。
  我更倾向于 最小必要修改：

局部不一致时，优先原位修正；仅当文档存在系统性结构问题、严重重复或多口径混杂时，才进行整体重构。

原有章节、术语、表格、设计理由，只要有效且不妨碍维护，就应保留。

三、建议增加的两条核心机制
机制 A：文档事实生命周期
我建议在现有 Skill 中增加一段可直接采用的规则：

## 文档事实生命周期

文档中的每条契约事实应具有明确的维护语义。

1. 首次建立：
   写入对应的权威章节，不重复定义。

2. 事实未变化：
   保留原文，不进行无意义的重写。

3. 实现事实变化：
   更新原有定义，删除已失效描述，
   检查关联章节及交叉引用。

4. 需求与实现冲突：
   保留有效目标契约，标记实现偏差，
   不得擅自将需求改写为当前实现。

5. 事实已废弃：
   确认依赖和引用关系后删除。
   有长期价值的决策依据另行保留。

6. 无法验证：
   保留待核状态与缺失证据说明，
   不得猜测、补造或静默删除。

禁止使用连续追加的方式维护
同一事实的多个历史版本。

机制 B：清理完成的可验证条件
目前 Skill 更重视执行流程，而不是最后是否真正消除了漂移。

我建议将下面几项作为最终验收标准：

- 准确性：所有已确认的实现事实均有证据来源。
- 唯一性：同一契约在目标文档内不存在相互竞争的定义。
- 完整性：清理没有丢失仍然有效的设计约束及理由。
- 一致性：目标文档的交叉引用和术语没有残留旧口径。
- 最小变更：所有非格式性变更均有明确必要性。
- 可追溯性：未解决的冲突与未验证项可以明确定位。
  这几条不需要引入复杂评分体系，也不必为每条设计事实建立长期 ID 数据库。
  四、我更推荐的 Skill 架构
  不建议把所有能力都堆进 doc-code-align，否则 Skill 自身也会开始膨胀。

可以把“文档治理”理解为两种不同职责。
doc-code-align
已有

负责对已经存在的技术文档进行审计、去重、校正，恢复与实现及有效契约的一致性。

触发：文档失真、版本混杂、需要集中清理

doc-lifecycle

可选的轻量补充

负责 Agent 在长期任务推进中如何更新已有文档、何时保留历史、何时清理过期内容。

触发：任务阶段转换、设计决策更新、里程碑完成

两者也不一定需要真的拆成两个 Skill。

更简单的方案是：

保留 doc-code-align 专注于事后治理；把“原位更新、单一事实源、不向契约正文追加进度流水”这三条约束写入 Agent 的全局工作规范。这样日常更新不必每次调用完整的五阶段审计流程。
五、下一版应该修改什么
我认为当前不需要推翻重做。建议采用 v1.1 小幅修正，优先完成以下四项：

1. 修正事实源规则，明确目标契约、实现事实与验证证据的区别。
2. 修正删除条件和人工确认边界，防止错误清理。
3. 将默认“重写”改为“最小必要修改”，降低无关 diff。
4. 优化裁定报告，避免为了减少正文冗余而制造更长的审计文档。
   接下来再考虑是否引入独立的 doc-lifecycle 机制，不需要一开始就设计庞大的文档管理体系。

最终判断：你这个 Skill 当前最大的风险，不是清理能力不够，而是清理权力过大。 它可以根据代码大范围改写文档，却没有充分区分哪些内容可以自动修正、哪些属于设计契约、哪些必须由用户裁决。

解决这个问题之后，再建立“有效事实原位更新”的机制，才能同时控制文档膨胀和技术口径漂移。
