# novel-master v1.2.0 — 章节生产与质量契约实施计划

> 基线：v1.1.0 冻结文档 + 1+7 Skill + 133 条测试（2026-07-25）
> 来源：`docs/prompt.md` 讨论 + 用户反馈修正（第三版，评分 9.2/10，基于第二轮评审修正）
> 性质：实施计划，非冻结文档；以下"项目现状确认"为**当前初步调查结论，执行时以仓库实况复核**

---

## 总体目标

引入**章节生产与质量契约**，使 Planner 能定义读者体验目标、Writer 能报告执行情况、Reviewer 能按维度独立验证、Style 能按场景提供弹性约束。

v1.1.0 解决的是"系统不会写错、串库和破坏设定"。v1.2.0 解决的是"系统能持续产出值得追更的章节"。

不在 v1.2.0 引入正式质量状态机和创作模式简化。

## 项目现状确认

> 以下为初步调查结论。Codex 执行时必须以仓库实况复核，不依赖计划假设。

1. **`chapter_plan` 的规范 Schema 当前在哪里？** 当前子 Skill 的输出结构在各自 SKILL.md 中通过 YAML 示例定义，`schemas/skill-result.schema.json` 仅管理通用交付物元数据信封（type/path/content_summary/deliverable_id/revision/content_hash/生命周期状态）。确认：`reader_experience` 不应写入 `skill-result.schema.json`，应在子 Skill SKILL.md 中定义新结构语义，并新建独立 Schema 文件管理校验。

2. **registry 是否承担业务输出契约注册？** 当前 `registry/packages/novel-master.json` 是包元数据（schema_version 2.0），`skill-ir.json` 是 IR 级资源清单。确认：子 Skill 输出契约当前由 SKILL.md YAML 示例定义，v1.2.0 新增结构首先在 SKILL.md 中定义语义，Schema 校验文件同步新增。

3. **`state/` 所有权是否排他？** v1.1.0 冻结文档明确 continuity-keeper 是 `state/` 唯一写入者。确认：质量状态不写入 `state/`。

## 阶段 0：建立质量基线（先于所有修改）

在修改任何冻结契约之前，先建立可量化的质量基线。

### 操作步骤

1. 选取 8~12 个代表性章节任务（覆盖 SETUP/TRANSITION/PAYOFF/CLIMAX 等关键静态类型各至少一个；TRANSITION 和 SETUP 最好各有两个，因为它们最容易被质量字段机械化）。分配：调优集 6~8 个，holdout 2~4 个。
2. 锁定同一 ContextPack 和大纲输入。
3. 用当前 v1.1 的 Planner/Writer/Reviewer 分别生成输出，每个任务生成 2~3 份（降低随机波动误判）。
4. 建立并**冻结**人工评分 Rubric（promise 具体性、payoff 是否真实发生、继续阅读动力、风格自然度、模板化程度、Reviewer 证据充分性）。Rubric 在生成 v1.2 候选结果前冻结，不根据 v1.2 输出调整标准。评分采用 1～5 分量表。
5. 记录完整可复现信息（git_commit、skill_package_revision、model_provider/name/version、decoding_parameters、seed、task_id、context_hash、outline_hash、generated_at）。
6. holdout 任务不参与后续字段和 Prompt 调优，仅用于最终冻结前验证。

### 产出

- `evals/baselines/v1.1-baseline/` — 8~12 组 Planner/Writer/Reviewer 输出快照（每组 2~3 份）。
- `evals/baselines/baseline_metadata.yaml` — 完整可复现元数据。
- `evals/baselines/quality-rubric.md` — 人工评分标准（1~5 分量表，冻结）。
- `evals/baselines/holdout_task_ids.yaml` — holdout 任务清单。

**基线完成后进入阶段 1。**

### 契约新增内容清单

#### A. `reader_experience` — 章节质量目标

定义位置：`chapter_plan`（Planner 输出）。

```yaml
reader_experience:
  chapter_role:
    primary: SETUP | ESCALATION | PAYOFF | REVEAL |
      REVERSAL | TRANSITION | RECOVERY | CLIMAX
    secondary: # optional
      - REVEAL
      - PAYOFF
    description: string

  promise: string # 本章向读者承诺什么，必填，具体到本章内容

  payoff:
    mode: FULL | PARTIAL | DEFERRED | NONE_JUSTIFIED
    description: string
    deferred_reason: string | null # mode=DEFERRED 必填
    justification: string | null # mode=NONE_JUSTIFIED 必填
    expected_payoff_window:
      type: NEXT_CHAPTER | WITHIN_CHAPTERS | ARC_END | VOLUME_END | null
      chapter_count: integer | null # type=WITHIN_CHAPTERS 时必填

  emotional_arc:
    target: string
    turning_point: string

  information_gain: # optional
    - target_id: string # 稳定引用 ID，如 "INFO-001"
      what: string
      significance: string

  tension_curve:
    type: RISING | WAVE | SPIKE | RELEASE | FLAT_JUSTIFIED
    description: string

  continuation_drive:
    type: QUESTION | DANGER | DECISION | REVELATION |
      EMOTIONAL | GOAL | NONE_JUSTIFIED
    description: string
    justification: string # type=NONE_JUSTIFIED 必填
```

#### B. 条件必需规则

| 模式            | `reader_experience` | 要求                                                                                                                     |
| --------------- | ------------------- | ------------------------------------------------------------------------------------------------------------------------ |
| FAST            | 可选                | 缺失时产生提示，不阻塞                                                                                                   |
| STANDARD        | 必需                | `chapter_role.primary`/`promise`/`payoff`/`emotional_arc.target`/`tension_curve.type`/`continuation_drive.type` 至少必填 |
| STRICT          | 必需                | 同上；`payoff.mode=DEFERRED` 必填 `deferred_reason`，`NONE_JUSTIFIED` 必填 `justification`                               |
| ADVISORY        | 按任务              | 取决于 Planner 判断                                                                                                      |
| v1.1 遗留章节卡 | 兼容                | 解析不崩溃；由加载器根据版本字段识别，不强制修改 v1.1 文件                                                               |

空 `reader_experience: {}` 在 STANDARD/STRICT 下视为非法。

> **实施注：条件必需中的 mode 判定是跨对象语义。`task.mode` 在 TaskEnvelope 中，而 `chapter_plan` 是独立对象。JSON Schema 负责单对象结构校验，跨对象条件由契约校验脚本（如 `validate_quality_contract.py`）负责。**

#### C. Writer 执行追踪

在 `chapter_report` 中增加逐项执行报告，取代全局自我评分：

```yaml
reader_experience_execution:
  target_execution:
    - target_ref: /reader_experience/promise # JSON Pointer 引用固定单项
      execution: PRESENT | PARTIAL | DEVIATED
      evidence_ref:
        source_type: CHAPTER_DRAFT # 证据来源类型
        deliverable_id: string
        revision: string
        scene_id: string | null
        paragraph_start: integer | null # 1-based，闭区间
        paragraph_end: integer | null # 非空 Markdown 块顺序编号
        json_pointer: string | null # YAML 结构证据时使用
        excerpt: string

    - target_ref: /reader_experience/information_gain/INFO-001 # 数组条目使用显式 target_id
      execution: PRESENT
      evidence_ref: ...

  deviations:
    - planned: string
      actual: string
      reason: string
  unplanned_effects:
    - effect: string
      evidence_ref: ... # 同上结构
```

**`target_ref` 引用规则**：

- 固定单项字段（promise/payoff/emotional_arc/tension_curve/continuation_drive）使用 JSON Pointer：`/reader_experience/promise`。
- 数组条目（information_gain）使用显式 `target_id`（如 `INFO-001`），target_ref 为 `/reader_experience/information_gain/INFO-001`。

**`evidence_ref.source_type` 枚举**：

```text
CHAPTER_DRAFT | CHAPTER_PLAN | CANON |
CONTEXT_PACK | STYLE_GUIDE | CHAPTER_REPORT
```

对于 YAML 结构证据使用 `json_pointer`，正文使用段落位置。段落编号：1-based、闭区间，段落按标准化 Markdown 的非空块顺序编号。

**Writer 只逐项报告是否执行和发生了什么，不给全局质量评分。是否达标由 Reviewer 决定。**

#### D. Reviewer 分层诊断

新增 `references/review-dimensions.md`：

```yaml
review_dimensions:
  CONTRACT_COMPLIANCE:
    question: "是否违反章节卡、Canon、知情范围或风格指南"
  NARRATIVE_SOUNDNESS:
    question: "因果、动机、冲突、信息揭示是否成立"
  READER_EXPERIENCE:
    question: "是否兑现 reader_experience、情绪曲线、阅读动力"
  CRAFT_EXECUTION:
    question: "对话、句式、AI 腔、角色声音"

# 任何 scope 下都必须执行的最小 Guardrail 扫描：
mandatory_guardrail_scan:
  - CANON_CONFLICT
  - KNOWLEDGE_STATE_VIOLATION
  - PROHIBITED_REVEAL
  - MAJOR_FACT_CONTRADICTION
```

> 注：`OWNERSHIP_OR_AUTHORITY_VIOLATION` 由确定性校验器（`validate_paths.py`、novel-master 路由）负责，不进入 Reviewer Guardrail。Reviewer 从文本内容无法可靠判断文件权限越界。

**契约变更**：`review_scope` 从 `string` 变为 `list[review_dimension]` 枚举（需冻结契约修订）。

Reviewer 输出分为两层：

```yaml
review_report:
  guardrail_results: # 独立于维度评审，始终输出
    status: PASS | WARNING | BLOCKED
    findings:
      - guardrail: CANON_CONFLICT
        severity: BLOCKER
        evidence_ref: ... # 与 Writer 的 evidence_ref 同结构
        assessment: string
        recommended_action: string

  dimension_results: # 必须恰好包含四个已注册维度
    - dimension: READER_EXPERIENCE
      status: PASS | WARNING | FAIL | NOT_EVALUATED
      reason_code: string | null # status=NOT_EVALUATED 时填写
      findings:
        - criterion: string
          evidence_ref: ...
          assessment: string
          recommended_action: string
          severity: INFO | WARNING | BLOCKER
```

未激活维度的 status 为 `NOT_EVALUATED`，并填写 `reason_code`（如 `NOT_REQUESTED`、`MISSING_PLAN_CONTRACT`）。`dimension_results` 必须恰好包含四个维度，每个维度出现一次。

**Guardrail 规则**：无论 review_scope 是什么，`mandatory_guardrail_scan` 中的项始终扫描。结果输出到 `guardrail_results`（独立于 dimension_results），不混入未激活维度的评审结果。

**review_scope 传递规则**：

- 由 novel-master 编排调用时：`review_scope` **必填**，由路由表显式传入。
- 用户直接调用 Reviewer：可根据请求推导；无法推导时才默认全量。

#### E. 场景风格调制

`chapter_plan.scenes[]` 新增字段：

```yaml
scenes:
  - scene_id: scene-01
    style_modulation_ref:
      string | null # 对应 style_guide.scene_modulations 中定义的 modulation_id
      # null = 仅使用 global defaults
```

**`style_modulation_ref` 必需规则**：

- FAST：可选，可为 null。
- STANDARD/STRICT：每个 scene 必填；无特殊调制时引用项目预定义的 `DEFAULT` modulation。
- 遗留计划：允许缺失。

##### 调制类型设计

不使用硬编码枚举。`novel-style` 定义项目级 modulation_id，使用稳定 `category` 枚举分类：

```yaml
scene_modulations:
  COMBAT_FAST:
    category: COMBAT
    overrides:
      sentence_rhythm:
        relative_to_global: SHORTER
      action_density:
        relative_to_global: HIGHER
  ROMANCE_TENSION:
    category: EMOTIONAL
    overrides:
      narrative_distance:
        relative_to_global: CLOSER
      sentence_rhythm:
        relative_to_global: LONGER
  CULTIVATION_BREAKTHROUGH:
    category: CLIMAX
    overrides: {}
```

其中：

- `category` 使用稳定枚举（COMBAT/EMOTIONAL/MYSTERY/TRANSITION/CLIMAX/EXPOSITION/DEFAULT）。
- `modulation_id`（如 `COMBAT_FAST`、`ROMANCE_TENSION`）允许项目自定义。
- Planner 引用 `modulation_id`，校验器确认引用存在于 `style_guide.scene_modulations`。
- `overrides` 只覆盖与全局默认值不同的字段，使用typed相对度量操作符，**不复述整个 Style Guide**；项目需要时补充具体自然语言约束。
- 示例具体值（如"平均 8-12 字"）仅作为说明，不作为通用模板要求。

##### 相对覆盖操作符定义

每个可调制字段使用类型化操作符，禁止通用 string：

| 字段                  | 允许操作符                    | 语义                   |
| --------------------- | ----------------------------- | ---------------------- |
| `sentence_rhythm`     | `SHORTER` / `LONGER` / `SAME` | 相对于全局默认句长     |
| `action_density`      | `HIGHER` / `LOWER` / `SAME`   | 相对于全局默认动作密度 |
| `narrative_distance`  | `CLOSER` / `FARTHER` / `SAME` | 相对于全局默认叙事距离 |
| `description_density` | `HIGHER` / `LOWER` / `SAME`   | 相对于全局默认描写密度 |
| `dialogue_ratio`      | `HIGHER` / `LOWER` / `SAME`   | 相对于全局默认对话占比 |

两层 override 合并时，更具体的层（章节 overrides > scene modulation > global defaults）覆盖更一般的层，不叠加。

##### 风格合并优先级

```text
章节临时明确授权（user/chapter_plan 显式 overrides）
  > 场景 modulation（scene_modulations 中当前 modulation_id 的 overrides）
  > 项目 global defaults（style_guide.md 全局默认值）
```

以下硬约束默认不可被 modulation 覆盖（需用户显式确认）：

```yaml
override_policy:
  protected_fields:
    - /narrative/viewpoint # 叙事视角
    - /narrative/person # 叙事人称
    - /characters/*/voice/core # 角色核心声音禁区
    - /constraints/prohibited_author_styles
    - /constraints/must_avoid
    - /constraints/content_safety
```

##### 跨文件校验

`style_modulation_ref` 引用 `style_guide.md` 中定义的对象。单文件 Schema 无法验证跨文件引用，由校验脚本 `validate_quality_contract.py` 执行：

```python
chapter_plan.scenes[].style_modulation_ref
  ∈ style_guide.scene_modulations.keys()
```

**契约变更**：`chapter_plan` 新增 `scenes[].style_modulation_ref`，`style_guide` 新增 `scene_modulations` 和 `override_policy`（需冻结契约修订）。

##### 确定性风格解析（可选辅助）

可增加 `scripts/resolve_style_profile.py`，根据全局默认值、scene modulation overrides、章节临时覆盖和 protected_fields，输出已解析的 `effective_scene_styles`。Writer 消费已解析结果，避免不同实现对合并优先级产生不同解释。这不是新增 Skill，只是确定性辅助层。

#### F. 兼容与迁移策略

所有业务交付物增加 `contract_meta`：

```yaml
contract_meta:
  schema_id: novel-master/chapter-plan
  schema_version: "1.2.0"
```

兼容规则：

- 缺少 `contract_meta` → 按 v1.1 legacy 解析 → 只读兼容 → STANDARD/STRICT 使用前要求升级。
- 同样适用于 ChapterPlan、ChapterReport、ReviewRequest、ReviewReport、StyleGuide。

具体使用场景：

| 使用场景             | 处理                                                                                                                          |
| -------------------- | ----------------------------------------------------------------------------------------------------------------------------- |
| 只查看旧章节卡       | 直接兼容读取                                                                                                                  |
| FAST 写作            | 可以带警告继续                                                                                                                |
| STANDARD/STRICT 写作 | 先由 Planner 生成 v1.2 修订版或补充质量契约（含 contract_meta）                                                               |
| Reviewer 审查旧正文  | 缺少 reader_experience 时，READER_EXPERIENCE 维度 status=`NOT_EVALUATED` 且 `reason_code: MISSING_PLAN_CONTRACT`，不标记 FAIL |
| v1.1 遗留文件        | 由加载器根据 contract_meta 缺失识别，不强制修改原文件                                                                         |

**reason_code 枚举**：

```text
NOT_REQUESTED            — 未在 review_scope 中激活
MISSING_PLAN_CONTRACT    — 旧版章节卡无 reader_experience
MISSING_SOURCE           — 评审目标文件缺失
STALE_REVISION           — revision 不匹配
INSUFFICIENT_CONTEXT     — ContextPack 信息不足
```

| `scripts/validate_quality_contract.py` | 跨对象条件校验（reader_experience 按模式必填、style_modulation_ref 引用存在、style_guide override_policy 冲突检测） |

### 4.3 v1.1 对照组 A/B 测试

**必须在同一模型、同一参数和尽可能接近的时间窗口中重新运行两个版本**，不能使用阶段 0 的快照对比后续模型输出。

使用阶段 0 锁定的同一批输入：

- 每个任务 v1.1 和 v1.2 各生成 2~3 份。
- 使用盲测、随机排列，Judge 不知道哪个是 v1.1。
- 评分采用 pairwise WIN / TIE / LOSS 判定。

对比维度：

- 章节目标具体性。
- 兑现质量。
- 连续阅读动力。
- 风格自然度。
- 模板化程度。
- 结构字段是否反而限制创作。

### 4.4 发布门槛

量化标准（评分 1～5 分，pairwise WIN/TIE/LOSS）：

1. 原 133 条治理测试全部通过（不可破坏 v1.1）。
2. 新增确定性测试 19 条全部通过。
3. v1.2 WIN + TIE ≥ 70%（即 LOSS ≤ 30%）。
4. v1.2 WIN ≥ 40%。
5. "自然度"和"模板化程度"不得出现系统性下降（>30% 任务 LOSS）。
6. 关键静态类型各至少有一个 WIN 或 TIE 样本：SETUP、TRANSITION、PAYOFF、CLIMAX。
7. holdout 任务也参与验证，结果统计独立；不得单独为 holdout 调优。
8. 至少 2～3 个 holdout 任务由人工复核，确认 Judge 判定与真实阅读体验一致。
