# OpenViking Memory 整理与治理

七个步骤按「止血 → 收紧入口 → 降成本 → 清存量」排布：体检基线、peer 止血与存量合并、
写入侧模板收紧、检索侧配置、sessions 分级保留、存量 events 瘦身、内容碰撞合并。

**这是菜单不是流水线**：用户点到哪步做到哪步，不默认全套推进。

## 总原则与红线

- 先只读巡检出方案，再等用户明确批准才做写操作，批准只覆盖被点名的范围和批次。

- 开工前锁定基线数字并做双备份，一份服务端 snapshot 加一份整树 tar 包并记录 md5，没有回滚路径不开工。

- 先试点再批量，试点挑最小且有代表性的对象，结果先给用户看再扩围。

- 每批做完立即对账验收，不过关就停在这批，不带着问题往下跑。

- 把 OpenViking 当文件系统管，移动和改名只走 `ov mv` 一类服务端命令，让向量记录随 URI 改键迁移。

- 禁止在磁盘上裸 mv 被索引的 workspace 目录，那样会脱钩 AGFS 元数据并让向量记录变孤儿。

- 禁止凭 CLI 输出措辞判定成败，删除和写回都要用目录残留、文件计数和 get 结果复核。

- 禁止重复提交服务端长任务，连接断开只断 CLI 等待，先查服务端任务状态再决定下一步。

- 汇报时把事实、推断、假设和未知分开，数字注明口径，文件数、字节和字符不混用。

- 密钥只验存在与格式，不读值也不回显，配置里用 `${VAR}` 引用已有环境变量，不落明文副本。

## 第一步 体检基线

- 通过用户已授权的通道进入目标实例，先确认 CLI 与服务端版本一致再开始盘点。

- 跑 `ov status` 并脱敏通读 ov.conf，记录检索次数、零结果率、模型配置和认证模式。

- 按 user 层和 peer 层盘点文件数与字节，统计 peer 总数、单项目拆出的 peer 数和各 memory 类型的分布。

- 聚合全部 memory_diff 的 adds、updates、deletes 和 skipped，判断记忆是不是只增不减。

- 聚合各 session 的 `.meta.json` 中 `llm_token_usage` 字段，算出抽取总 token、commit 次数和单次均值，先把写入侧成本算成账。

- 抽查摘要新鲜度、命名空间里混入的旧备份目录和 experiences 是否长期为零这几类结构信号。

- 对照官方文档核实机制口径，重点看 peer 语义、跨 peer 召回降权、没有 TTL 和模板加载方式这四处，文档与源码打架时以实机实测为准。

- 输出分级问题清单和建议动手顺序，每项写清收益、风险和回滚方式，等用户挑选。

## 第二步 peer 止血与存量合并

- 先止血再搬存量，给每个仓库根目录写一份 `.openviking/config.json` 把 peer.id 固定下来，格式为 `{"version": 1, "peer": {"id": "<id>"}}`。

- peer.id 不另起新名，对齐存量最大的 peer，有 GitHub origin 的仓库沿用现存 git 派生名，本地和局域网仓库用短名。

- 一次性目录、日期型会话目录和非仓库目录不写配置，并提醒用户今后的一次性任务不要在会派生 peer 的目录里跑。

- 明确告诉用户写 peer.id 只改变今后新记忆的落点，存量不会自动搬家，变体是否并入同一 peer 有争议时等用户拍板。

- 存量合并用 `ov mv` 做目录递归合并，向量记录改键迁移且零重新 embedding，目标父目录的 L0 和 L1 摘要会自动入队重建。

- 批次按 scope 从小到大排，最大的项目放最后，每批前后都重新计数。

- 碰撞先分级再处理，`.abstract.md` 和 `.overview.md` 这类摘要碰撞由服务端重建可以放行，内容文件碰撞单独列清单交用户定。

- 每批合并后抽样跑 `ov find`，确认召回落在新 URI，再对各正典子树跑 `ov system consistency`。

## 第三步 写入侧模板收紧

- 先把现行模板与官方内置模板逐字 diff，分清鼓励拆分的措辞到底来自官方还是用户自订，再谈收紧。

- 收紧只改描述区，显著性门槛只留决策、承诺、安排、里程碑和改变状态的结果，例行操作步骤、被后续状态覆盖的中间进展和无结论问答不抽。

- 同一工作项在一次对话里只成一个事件，把 started、blocked、resumed 和 completed 合成一条，summary 落在最终结果上。

- 给单次对话设事件数软上限，实测口径取 5 个，并把官方拆成四条的例子翻转成合并成一条的正例。

- ranges 字段补上优先用一整段覆盖整个工作项，跨工作项的独立决策仍然分开不合并。

- 目录、文件名模板、content_template 和 operation_mode 这些结构区逐字不动，改前备份原模板并核对哈希。

- 模板由进程级单例缓存加载，写回后必须重启服务才生效，把这次重启与其他待生效配置并成一次并提前告知用户。

- 模板只影响今后抽取，存量问题另走瘦身流程，效果等数日的日增曲线出来再下结论。

## 第四步 检索侧配置

- 先查 ov.conf 里 rerank、query_planner 和 vlm 三段的现状，未配 reranker 时 `ov search` 会退化成无重排的 QUICK。

- 选接法先查服务端自带客户端支持哪些 provider，不要默认外部代理库支持目标厂商，实测 litellm 没有 DashScope 的 rerank 通路，正解是自带的 openai 兼容客户端按 api_base 路径分流报文。

- 改配置前先直打目标端点做探针测试，用一个目标文档加两个干扰文档验排序，再走服务端同路径复测同一组探针，两段分数一致才算真通。

- rerank 失败会静默回退向量分，没有报错不证明在工作，生效证据要看探针分数一致和 `ov search` 实际走 THINKING。

- query_planner 在每次 THINKING 搜索都会被调用，单独配快而便宜的模型，不要让它占用主 VLM 的额度通道。

- vlm.max_tokens 按抽取被截断的实证来抬，改前先实测目标端点接受新上限再写配置。

- 每段配置单独留一份 ov.conf 备份，api_key 一律写 `${VAR}` 引用，重启后逐段读回配置并实跑一条复合意图搜索验收。

- planner 的调用在 INFO 日志里可能无痕，这类行为侧证据偏弱时如实标注，不拿配置读回冒充全链路实证。

## 第五步 sessions 分级保留

- 先把机制讲清再谈删，transcript 正文不进向量索引，单次 search 的成本与 sessions 总量无关，成本大头在写入侧的每次 commit 抽取。

- 例外只有一条，带 session_id 的 search 会加载当前会话上下文做意图分析，这笔成本与当前会话大小相关。

- 按最后活动时间分级，近期批不动，温批只迁 history 原件并保留 session 根摘要、`.meta` 和全部 memory_diff，冷批整 session 打包出库。

- 冷存先打 tar.gz 并同目录放 manifest 和 md5，回读验证能从包里取到 `.meta` 才算存好。

- 冷批用 `ov session delete` 逐个清索引，验收看四点，目录零残留、已删 id 的 get 返回 NOT_FOUND、记忆文件数删除前后不变、consistency 为 ok 且召回正常。

- 温批批量前先拿单个 session 做微试点，验证磁盘上移走 history 后 get、consistency 和召回是否正常，这条没有实证前不批量。

- 压缩率先实测再估空间，同盘冷存大约只释放一半，要全额腾空就把迁出本机列为选项让用户定去向。

- 滚动保留先手动跑两三轮再谈自动化，一次性会话单独拉清单，可直接删的不混进冷存批。

## 第六步 存量 events 瘦身

- 先做存量画像，统计 events 总数、user 与 peer 分布、正文总字符和 ChatLog 占比，再决定三层的投入。

- L1 去 ChatLog 是确定性瘦身，每条只保留 Summary 段加上原 MEMORY_FIELDS 块，整段删掉 ChatLog，逐字校验 Summary 不变才算过。

- L1 的追溯不受影响，聊天原文还留在 sessions 原料层，瘦身后摘要和向量改为按干净文本重建。

- L2 只删高置信重复，范围限同 peer、同标题、同日重复抽取和正文近重复，清单先抽检再用 `ov rm` 执行。

- L3 状态链合并逐簇判读，有终态且覆盖中间态时把中间态的关键节点写成过程节点一节并入终态事件再删中间态，未完结的链不动。

- 历轮评审结论和用户裁定确认类事件是独立资产，列为 L3 禁区，同名成链不等于冗余是这一步的第一判断。

- 试点先标定真实删除率再估批量，实测 L3 删除率只有约百分之五到十，主收益在 L1，不要按理论上限向用户承诺。

- 批量用可续跑脚本按 scope 从小到大执行，逐个写 JSONL 进度并在收尾落一份 DONE 汇总，单个失败记录原因后继续不中断，重跑时已干净的文件自动跳过。

- L1 运行器在本技能的 `scripts/l1_runner.py`，已在 OpenViking v0.5.2 上跑完一轮全量；换实例先改文件头部的 `BASE` 和 `WORK` 两个路径。它把正文写到下划线临时 URI 再用 `ov mv` 移回真实路径，无 ChatLog 的文件静默跳过（幂等）。

- 批量前把标题同时含空格和斜杠的事件单独分出来，这类文件会多出一级含空格目录，是写回失败和孪生文件的高发形态。

- 批量后专门核对原件是否真被替换，磁盘上多出的下划线孪生文件逐个列清，收尾方案交用户批准再动。

## 写回规程

- 写回正文必须带上原文件完整的 MEMORY_FIELDS 块，漏带时服务端只补一个 `{"version": 1}` 存根，`source_extraction_id` 和 `ranges` 这些溯源字段会全丢。

- 对整条相对路径判空格而不是只看末段文件名，任一段含空格都先写下划线临时 URI 再用 `ov mv` 移回真实路径。

- `ov mv` 保留路径原文且向量记录随迁，移回后删掉空的下划线目录并复查 consistency。

- 写回会触发隐私替换，个别词在磁盘上会变成 `{{ov_privacy:...}}` 令牌形态，API 读回可以还原，验收时见到令牌不要误判为内容损坏。

- 含空格路径的文件不要信 `ov read` 的输出，那是加工过的渲染，验收以磁盘原文加 `ov grep` 和 `ov find` 为准。

- 写回后服务端可能重复回附 MEMORY_FIELDS 块，对账时单独统计块数分布，溯源没丢也要把这个现象报给用户决定是否清理。

## 内容碰撞的人工合并

- 内容碰撞的两版互补时做并集合并，以信息量大或状态最终的版本为底，补入另一版独有段落，被同日后续裁定取代的中间口径要标注清楚。

- 合并稿逐条保留原文不改写不缩写，写回后回读正文逐字比对，再用 `ov grep` 实查合并独有字符串各就其位。

- 被覆盖版本只从合并前的 snapshot 和 tar 备份里取原文，取不到就停下来报用户，不凭印象重构。

- 用户只点了名的文件才做内容合并，同批其他被覆盖文件保持原状并在汇报里列明可恢复位置。

## 验收对账与汇报

- 文件守恒是第一关，变更前后总数对账，每个差额都要归因到摘要碰撞、内容碰撞、孪生文件或期间新抽取，给不出来源的差额不放行。

- 字节账和文件数分开报，DONE 汇总、残留清单和失败清单逐条列，不用一句全部成功盖过去。

- consistency 要看 missing 明细时加 `-o json`，表格输出会把明细吞掉。

- 抽检样本从动工前备份里取原件逐字比对关键段落，同时确认 MEMORY_FIELDS 的溯源字段还在。

- 召回抽查用有代表性的真实查询，确认目标条目落在新 URI 且排名没有塌，瘦身类操作还要对比处理前后的名次变化。

- 备份的 md5 在收尾时复测一遍与动工前记录比对，一致才宣布可回滚。

- 汇报结论先行，把未决项和下一步选项单独列出，每个选项写清动作和代价，等用户点选。

## 已知坑

- 复杂脚本不要嵌在 SSH 的引号里拼 heredoc 和尖括号，写成本地文件用 stdin 管道送进容器执行。

- 容器里的 shell 是 dash 且缺 ps 等常用命令，查进程存活扫 `/proc` 下的 cmdline，容器时间是 UTC，对时间戳先换算时区再比较。

- `ov session delete` 这类命令的输出是表格，用关键词匹配输出判定成败会全量误报，一律以实查为准。

- 命名空间里躺着的旧备份目录会被当成现行记忆召回，发现后先报用户，挪出命名空间要单独批准再动。

- 语义队列重建和 reindex 都是服务端任务，提交后记下任务 id，状态以服务端查询为准。
