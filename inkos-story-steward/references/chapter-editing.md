# 章节修改流程（CHAPTER_EDIT 模式）

> 本文件在 CHAPTER_EDIT 模式下加载。定义修改 `chapters/*.md` 的判断和执行流程。

---

## 关键约束（InkOS v1.7.x 源码限制）

> **`write sync` 只能同步最新已持久化章节。** 目标不是最新章时，InkOS 直接报错：
> "Only the latest persisted chapter can be synced safely."

此约束决定了所有事实修改的路由。

---

## 修改类型判断树

收到正文修改请求后，按以下顺序判断：

```
用户请求修改正文
│
├─ 修改是否改变事实/行为结果？
│  │
│  ├─ 否 → 类型 A：纯文风修改（任何章节均可）
│  │
│  └─ 是 → 目标是最新章？
│     │
│     ├─ 是（最新章）→ 类型 B：最新章事实修改
│     │
│     └─ 否（非最新章）→ 修改是否影响后续章节的因果？
│        │
│        ├─ 否（仅本章内部事实，后续不依赖）→ 类型 B2：非最新章局部事实
│        │
│        └─ 是（后续章节依赖此事实）→ 类型 C：修改历史因果
```

---

## 类型 A：纯文风修改

### 判断标准
- 删除重复描述
- 调整句子结构/措辞
- 修改错别字
- 调整段落顺序（不改变事件顺序）
- 增加/删减环境描写
- 不改变任何事实、行为结果、人物关系

### 适用章节
任何章节（最新章或历史章均可）。

### 操作流程
1. 输出变更影响分析（简化版：标注为纯文风，无事实影响）
2. 直接编辑正文文件
3. 建议运行审查确认：

```bash
inkos audit [book-id] [chapter]
```

### 风险提示
- 风险极低
- 无需 sync/rewrite
- 但如果误判（实际改变了事实），后续状态会不一致

---

## 类型 B：最新章事实修改

### 判断标准
- 目标是最新已持久化章节
- 改变本章事实（谁拿到了物品、谁知道了秘密、人物关系变化、伏笔揭示、角色状态改变）

### 操作流程
1. 输出完整变更影响分析
2. 编辑正文文件
3. **必须**执行状态同步：

```bash
inkos write sync [book-id] <chapter>
```

4. 验证 sync 结果（检查退出码，运行 `inkos status`）

### `write sync` 说明
InkOS 的 `write sync` 会根据编辑后的正文重建 truth 文件和 SQLite 索引。
**仅对最新章有效。**

### 风险提示
- 中等风险
- 如果后续章节依赖被修改的事实（此时无后续章节），风险可控
- 确认修改的确实是最新章（通过 `chapters/index.json` 验证）

### 确认要求
- 向用户说明修改了哪些事实
- 说明 sync 的作用

---

## 类型 B2：非最新章局部事实修改

### 判断标准
- 目标不是最新章
- 改变本章事实，但后续章节不依赖此事实

### 操作流程
1. 输出完整变更影响分析
2. **明确告知用户**：`write sync` 不能用于非最新章
3. 评估两种路径：

**路径 A（推荐）**：如果可以接受，通过最新章节的正文变化来体现修正，然后对最新章执行 sync。

**路径 B**：如果必须修改此历史章的正文，直接编辑文件，但明确标记：
- 此修改不会被 InkOS 状态系统感知
- `state/current_state.json` 和 `memory.db` 中的记录不会更新
- 后续 `inkos audit` 可能报告不一致
- 如果需要完全一致性，必须升级为类型 C（rewrite）

4. 如果用户选择路径 B，编辑文件后建议：
```bash
inkos audit [book-id]    # 检查是否产生新的不一致
```

### 风险提示
- 中高风险
- 状态系统与实际正文不一致
- 可能导致后续写作引用错误的历史记录
- 绝不可对非最新章调用 `write sync`（会报错）

---

## 类型 C：修改历史因果

### 判断标准
- 修改第 N 章，而后面已经写到第 N+X 章
- 修改会影响后续剧情的因果链
- 例如：改变角色死亡/存活、改变关键物品归属、改变联盟关系

### 操作流程
1. 输出完整变更影响分析（必须列出受影响的后续章节）
2. **必须获得用户明确确认**
3. 建议先备份：

```bash
inkos book backup [book-id]
```

4. 执行重写：

```bash
inkos write rewrite [book-id] <chapter>
```

5. 重写完成后检查新生成的章节

### `write rewrite` 说明
InkOS 会：
1. 恢复到前一章的状态快照
2. **删除目标章及所有后续章节**
3. 从目标章开始重新生成

### 风险提示
- **高风险，不可逆**
- 会删除目标章之后的所有章节
- 重写后的内容可能与原作者意图有偏差
- 需要 LLM 配置正常工作

### 确认要求（强制）
必须向用户明确说明：
1. 将删除第 N 章之后的所有 X 章内容
2. 这些章节将需要重新生成
3. 重新生成的内容可能与原版不同
4. 建议先执行 `inkos book backup`
5. 等待用户明确说"确认"或"执行"后才继续

---

## 路由速查表

| 章节位置 | 修改类型 | 操作 | 禁止 |
|----------|----------|------|------|
| 任何章节 | 纯文风 | 直接编辑 + audit | — |
| 最新章 | 改变事实 | 编辑 + `write sync` | — |
| 非最新章 | 改变事实，后续不依赖 | 评估路径 A/B，不可 sync | 调用 `write sync` |
| 非最新章 | 改变事实，后续依赖 | backup + `write rewrite` | 手改后保留后续 |

---

## 特殊情况

### 修改最新章（无后续章节）
如果修改的是最后一章，类型 B 直接适用：
- 改变事实 → 编辑 + `write sync`
- 不需要 rewrite（没有后续章节需要删除）

### 批量修改多章
- 每章独立判断修改类型
- 如果多章修改存在因果关联，按最严重的类型处理
- 建议从最早的章节开始处理
- 非最新章的事实修改不能 sync，需要逐章评估

### 修改后验证
完成修改后，建议：
```bash
inkos audit [book-id]          # 审计最新章
inkos status [book-id]         # 确认状态正常
```

### 如何判断最新章
读取 `chapters/index.json`，取最大编号对应的章节文件。如果 index.json 不存在或为空，则无章节（不应进入 CHAPTER_EDIT 模式）。
