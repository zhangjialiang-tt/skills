# 章节修改流程（CHAPTER_EDIT 模式）

> 本文件在 CHAPTER_EDIT 模式下加载。定义修改 `chapters/*.md` 的判断和执行流程。

---

## 修改类型判断树

收到正文修改请求后，按以下顺序判断：

```
用户请求修改正文
│
├─ 修改是否改变事实/行为结果？
│  │
│  ├─ 否 → 类型 A：纯文风修改
│  │
│  └─ 是 → 修改是否影响后续章节的因果？
│     │
│     ├─ 否（仅影响本章内部事实）→ 类型 B：改变本章事实
│     │
│     └─ 是（后续章节依赖此事实）→ 类型 C：修改历史因果
```

---

## 类型 A：纯文风修改

### 判断标准

- 删除重复描述
- 调整句子结构/措辞
- 修改错别字
- 调整段落顺序（不改变事件顺序）
- 增加/删减环境描写
- 不改变任何事实、行为结果、人物关系

### 操作流程

1. 输出变更影响分析（简化版：标注为纯文风，无事实影响）
2. 直接编辑正文文件
3. 建议运行审查确认：

```bash
inkos audit [book-id] [chapter]
```

### 风险提示

- 风险极低
- 无需 sync/rewrite
- 但如果误判（实际改变了事实），后续状态会不一致

---

## 类型 B：改变本章事实

### 判断标准

- 谁拿到了物品
- 谁知道了秘密
- 人物关系变化
- 伏笔被提前揭示
- 角色受伤/死亡情况改变
- 时间线微调（不影响后续）

### 操作流程

1. 输出完整变更影响分析
2. 编辑正文文件
3. **必须**执行状态同步：

```bash
inkos write sync [book-id] <chapter>
```

4. 检查后续章节是否受影响（读取后续 1-3 章确认）

### `write sync` 说明

InkOS 的 `write sync` 会根据编辑后的正文重建 truth 文件和 SQLite 索引。

### 风险提示

- 中等风险
- 如果后续章节依赖被修改的事实，`write sync` 只重建当前章的状态，不会自动修复后续矛盾
- 发现后续矛盾时，需要评估是否升级为类型 C

### 确认要求

- 向用户说明修改了哪些事实
- 说明 sync 的作用
- 如果检测到后续章节可能受影响，提醒用户

---

## 类型 C：修改历史因果

### 判断标准

- 修改第 N 章，而后面已经写到第 N+X 章
- 修改会影响后续剧情的因果链
- 例如：改变角色死亡/存活、改变关键物品归属、改变联盟关系

### 操作流程

1. 输出完整变更影响分析（必须列出受影响的后续章节）
2. **必须获得用户明确确认**
3. 建议先备份：

```bash
inkos book backup [book-id]
```

4. 执行重写：

```bash
inkos write rewrite [book-id] <chapter>
```

5. 重写完成后检查新生成的章节

### `write rewrite` 说明

InkOS 会：

1. 恢复到前一章的状态快照
2. **删除目标章及所有后续章节**
3. 从目标章开始重新生成

### 风险提示

- **高风险，不可逆**
- 会删除目标章之后的所有章节
- 重写后的内容可能与原作者意图有偏差
- 需要 LLM 配置正常工作

### 确认要求（强制）

必须向用户明确说明：

1. 将删除第 N 章之后的所有 X 章内容
2. 这些章节将需要重新生成
3. 重新生成的内容可能与原版不同
4. 建议先执行 `inkos book backup`
5. 等待用户明确说"确认"或"执行"后才继续

---

## 特殊情况

### 修改最新章（无后续章节）

如果修改的是最后一章，类型 B 和类型 C 的区别消失：

- 改变事实 → 编辑 + `write sync`
- 不需要 rewrite（没有后续章节需要删除）

### 批量修改多章

- 每章独立判断修改类型
- 如果多章修改存在因果关联，按最严重的类型处理
- 建议从最早的章节开始处理

### 修改后验证

完成修改后，建议：

```bash
inkos audit [book-id]          # 审计最新章
inkos status [book-id]         # 确认状态正常
```
