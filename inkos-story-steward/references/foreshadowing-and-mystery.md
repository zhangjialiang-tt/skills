# 伏笔与谜题设计方法

> 本文件定义如何判断伏笔和谜题系统的质量。
> 在 PREBUILD 阶段 8 和 ACTIVE_MAINTENANCE 的伏笔相关操作中参考。

---

## 伏笔 vs 谜题 vs 悬念

- **伏笔**：前文埋下线索，后文揭示其真正意义。读者回看时"原来如此"。
- **谜题**：读者知道有问题但不知道答案。驱动好奇心。
- **悬念**：读者知道可能发生的坏事，等待是否发生。驱动紧张感。

三者可以重叠：一个伏笔在揭示前是谜题，在逼近时是悬念。

---

## 伏笔质量判断

### 1. 公平性测试

- ❌ 坏：揭示时读者感觉"被耍了"——关键信息从未出现
- ✅ 好：揭示时读者感觉"我怎么没想到"——线索一直在，但被误导了

检查：
- 回收时，能否指出至少 2 处前文中的公平线索？
- 这些线索在当时是否有其他合理解释？（如果有 → 好的误导）
- 如果删除所有线索，揭示是否变成"突然事件"？

### 2. 意义变化测试

- ❌ 坏：揭示后，前文的理解没有变化（"哦，他其实是好人"——然后呢？）
- ✅ 好：揭示后，读者对前文多个事件的理解发生反转

检查：揭示后，至少 3 个前文事件的含义是否改变？

### 3. 知识不对称设计

每个伏笔/谜题必须明确：

| 维度 | 内容 |
|------|------|
| 读者所知 | 读者到这里应该知道什么 |
| 主角所知 | 主角到这里知道什么 |
| 对手所知 | 对手知道什么 |
| 真相 | 实际是什么 |
| 错误解释 | 读者最可能形成的错误理解 |
| 信息释放顺序 | 哪些事实先给读者、主角、对手，哪些必须延后 |

检查：
- 读者和主角之间是否有信息差？（如果有 → 可以制造悬念）
- 读者和对手之间是否有信息差？（如果有 → 可以制造紧张）
- 错误解释是否合理？（如果读者不可能形成错误解释 → 悬念太弱）

### 4. 回收时机测试

- ❌ 坏：回收太早（读者还没积累足够好奇心）或太晚（读者已经忘了或不在乎了）
- ✅ 好：回收在读者"最想知道"的时刻

检查：
- 回收位置是否在某个冲突升级的节点？（不是平静期）
- 回收后是否立即产生新的问题或行动？（不是"哦"然后继续）
- 如果提前 10 章回收，是否太早？如果推迟 10 章，是否太晚？

### 5. 不依赖巧合

- ❌ 坏：伏笔的回收依赖"恰好有人看到了""恰好那个东西在那里"
- ✅ 好：回收是某个角色主动行动的结果

检查：回收是否由角色的选择驱动？如果删除角色的主动行为，回收是否仍然发生？

## 伏笔系统设计

### 层次结构

好的伏笔系统有层次：

- **短线伏笔**：5-15 章内回收（满足即时好奇心）
- **中线伏笔**：一卷到两卷内回收（驱动追读）
- **长线伏笔**：跨多卷回收（构成核心谜题）

比例建议：短线 50%，中线 30%，长线 20%。

### 伏笔账本

每个伏笔必须记录：

| 字段 | 说明 |
|------|------|
| 编号 | H001, H002... |
| 类型 | 伏笔/谜题/悬念 |
| 前台问题 | 读者看到的问题 |
| 后台真相 | 实际答案 |
| 埋设位置 | 第几章/什么场景 |
| 公平线索 | 至少 2 处 |
| 误导设计 | 读者最可能的错误解释 |
| 回收条件 | 什么事件触发回收 |
| 回收位置 | 第几卷/大约第几章 |
| 回收后意义变化 | 什么改变了 |
| 信息释放顺序 | 各阶段允许谁知道什么 |
| 状态 | 未埋设/已埋设/已回收 |

### 与 InkOS 的映射

伏笔账本最终映射为 `pending_hooks.md` 的初始种子。但注意：
- 建书前：写入编译包 `<design-root>/compile/inkos/pending_hooks.md`
- 建书后无章节：可直接修正 `pending_hooks.md`
- 建书后有章节：通过 `current_focus.md` 推进，让 InkOS 结算

## 常见伏笔设计错误

1. **伏笔过多不回收**：每卷埋 10 个，只回收 3 个 → 读者失去信任
2. **所有伏笔同一类型**：全是"他其实是 XX 的儿子" → 可预测
3. **回收不改变任何东西**：揭示了秘密但对剧情无影响 → 无意义
4. **线索太明显**：读者第 3 章就猜到了，第 50 章才揭示 → 拖沓
5. **线索太隐晦**：回看也找不到线索 → 不公平
6. **回收依赖巧合**：恰好有人在旁边听到了 → 不可信
