## 核心判断

Codex 官方把 Goal 定义为一个**线程级、持续存在、基于证据判定完成的契约**。它适合“终点明确、路径未知”的任务，例如复杂调试、性能优化、迁移、跨文件重构和研究复现；一次性修改、纯探索、尚未确定方向的架构讨论，普通 Prompt 或 Plan Mode 更合适。

一个高质量 Goal 不是：

> 告诉 Agent 接下来做什么。

而是：

> 定义最终必须达到什么状态、用什么证据证明、哪些东西不能破坏，以及走不通时如何诚实停止。

---

# 一、好 Goal 的六个组成部分

Codex 官方总结了六个核心要素：Outcome、Verification surface、Constraints、Boundaries、Iteration policy 和 Blocked stop condition。

## 1. Outcome：最终状态

描述“完成后系统是什么样”，不要只描述动作。

弱：

```text
/goal 优化压缩模块
```

强：

```text
/goal 使压缩模块稳定支持1280×1024@50Hz输入
```

进一步增强：

```text
压缩模块在1280×1024@50Hz输入下连续处理10帧，
无丢帧、死锁、AXI协议错误或输出长度异常。
```

Goal 应描述**状态**，而不是“分析、研究、尝试、检查”等过程词。

---

## 2. Verification surface：验收证据

这是 Goal 最重要、也最容易遗漏的部分。

证据可以是：

- 测试命令及其结果；
- benchmark 指标；
- 仿真回归报告；
- 板级采样数据；
- 生成的文件或报告；
- 日志、波形、CRC、diff；
- 明确的人工检查项。

Codex 官方强调，Goal 不能因为模型“认为大概完成了”而结束，必须由测试、文件、日志、benchmark 或生成物等具体证据支持。

例如：

```text
通过以下证据验证：

1. run_phase2_regression.sh 全部 PASS；
2. 1280×1024 测试帧输出与 C++ reference model 逐字节一致；
3. 板上连续运行10帧，accepted == cmd_len；
4. 每帧均观察到 m_axis_read_data_tlast；
5. GVSP接收端 bad_fcs == 0。
```

“代码看起来正确”不是证据。

---

## 3. Constraints：不能破坏什么

只写目标，不写约束，Agent 很容易通过扩大改动范围“完成任务”。

常见约束包括：

```text
- 不改变现有顶层接口；
- 不改变DDR帧布局；
- 不修改公共API；
- 不降低现有测试覆盖率；
- 不删除或弱化测试来获得PASS；
- 不通过硬编码特定测试数据规避问题；
- 保持现有子模块回归全部通过。
```

约束最好写成**可验证的不变量**，少使用：

```text
保持代码优雅
确保实现健壮
遵循最佳实践
```

这些词无法客观判定。

---

## 4. Boundaries：允许动哪里

明确：

- 可以读取哪些目录；
- 可以修改哪些模块；
- 可以运行哪些工具；
- 哪些文件是冻结基线；
- 哪些操作需要用户批准。

例如：

```text
允许修改：
- rtl/read_path/**
- tb/read_path/**
- scripts/run_read_regression.py

只读参考：
- rtl/vendor/**
- docs/protocol/**
- cpp/reference_model/**

禁止修改：
- 第三方axi_dma源码；
- 已冻结的帧格式；
- 量产寄存器地址定义。
```

边界不是越窄越好。过窄会让 Agent 无法修复真正位于上游的问题。官方建议 Goal 应当“足够窄以便审计，但足够开放以支持发现”。

因此可以写：

```text
优先限制在 read_path；若证据表明根因位于相邻模块，可以扩展调查，
但修改前必须说明证据和影响范围。
```

---

## 5. Iteration policy：每轮如何选择下一步

Goal 的价值不只是记住目标，更在于让 Agent 根据上一次实验结果选择下一步。

推荐写法：

```text
每轮按以下方式推进：

1. 先建立或更新当前根因假设；
2. 优先执行能最大幅度区分候选根因的最小实验；
3. 一次只引入一个可归因的变量；
4. 修改后先运行最小相关测试，再运行完整回归；
5. 根据新证据决定继续、回退还是更换假设；
6. 不重复已经被证据否定的路径，除非出现新的反证。
```

这一段可以显著减少：

- 盲目试错；
- 一次修改多个地方；
- 修复后无法判断哪项改动有效；
- 重复走已经失败的路线。

Codex 官方给出的增强 Goal 也建议每次迭代记录“改了什么、证据显示什么、下一项最佳实验是什么”。

---

## 6. Blocked stop condition：什么时候允许停

不要只写：

```text
继续直到完成
不要停下来
```

这会导致无效循环、重复尝试或为了宣布完成而降低标准。

应明确：

```text
以下情况视为阻塞，而不是完成：

- 必要测试环境无法运行；
- 缺少输入数据、硬件或授权；
- 冻结接口与验收目标存在直接冲突；
- 所有合理路径均已被证据否定；
- 继续推进必须修改当前禁止修改的范围。

阻塞时停止修改并提交：

1. 已尝试路径；
2. 每条路径的证据；
3. 当前最可能根因；
4. 尚未验证的假设；
5. 阻塞原因；
6. 解除阻塞所需的最小输入。
```

Codex 官方明确区分了“成功完成”和“达到预算或遇到阻塞”：后者应总结进度和下一步，不能伪装成完成。

---

# 二、高效、准确、稳定分别靠什么

## 高效：控制信息密度

Goal 只保留当前任务特有的信息：

```text
目标
证据
约束
边界
迭代规则
阻塞规则
```

下面这些长期规则不要反复塞进 Goal：

- 仓库结构；
- 通用编码规范；
- 构建命令；
- 命名习惯；
- 团队约定；
- 全局禁止事项。

它们更适合放入 `AGENTS.md`。Codex 官方也建议把仓库布局、测试命令、工程规范、禁止事项和通用完成标准放在 `AGENTS.md` 中，让其跨任务自动生效。

---

## 准确：先定义证据，再定义动作

推荐顺序：

```text
先问：怎样证明问题解决了？
再问：Agent需要做什么？
```

而不是：

```text
先列出一长串修改步骤，
最后补一句“确保测试通过”。
```

因为修改步骤可能基于错误假设，而验收证据通常更稳定。

---

## 稳定：固定终点，开放路径

稳定的 Goal 应做到：

```text
终点固定
验收固定
约束固定
探索路径开放
```

不要把未经验证的根因写成事实。

不推荐：

```text
/goal 修复由于status FIFO丢失导致的tlast问题
```

推荐：

```text
/goal 找到并修复导致板上read path无法产生tlast的根因。
当前线索是status FIFO empty，但不得将其视为既定根因，
必须通过波形、计数器或最小实验验证。
```

这样即使初始判断错误，Goal 仍然有效。

# 三、使用 Goal 的实战技巧

## 1. 一个 Goal 只维护一个主完成条件

可以有多个验收项，但最好只有一个主目标。

不推荐：

```text
修复tlast、重构压缩模块、提高性能、补文档、增加新协议
```

这实际上是五个 Goal。

更好的拆分：

```text
Goal 1：找到并修复tlast根因
Goal 2：完成read path结构重构
Goal 3：完成性能优化
```

前一个 Goal 的输出可以成为下一个 Goal 的输入。

---

## 2. 模糊任务先 Plan，再 Goal

Codex 官方建议复杂、含糊或难以描述的任务先使用 Plan Mode，让 Agent 收集上下文、提出必要问题并形成实施计划；Goal 更适合在目标和完成条件已经基本稳定后启动。

推荐流程：

```text
Ask / Plan
→ 探索代码与问题
→ 冻结目标和验收标准
→ 生成Goal
→ 启动Goal
→ 证据驱动迭代
```

Goal 不应该承担“帮我决定到底要做什么”的职责。

---

## 3. 不要把完整 Plan 复制成 Goal

Plan 描述路线：

```text
第一步做A
第二步做B
第三步做C
```

Goal 描述完成契约：

```text
达到X
通过Y证明
不能破坏Z
路径可以根据证据调整
```

如果把 Plan 完整塞进 Goal，Agent 可能在事实已经变化后仍机械执行旧步骤。

可以引用计划：

```text
以 docs/PLAN.md 作为初始实施路线，但它不是冻结事实。
若新证据否定计划中的假设，应调整实施路径，同时保持本Goal的验收条件不变。
```

---

## 4. 每项验收最好对应一个检查动作

例如：

```text
验收：接口没有变化
检查：比较修改前后顶层端口和寄存器定义

验收：没有回归
检查：运行 scripts/run_regression.sh

验收：输出正确
检查：与 cpp/reference_model 输出逐字节比较
```

这比单独列一个“验收标准”列表更可靠。

---

## 5. 优先使用行为标准，不要指定实现细节

除非架构已经冻结，否则不要过早要求：

```text
必须增加一个三级FIFO
必须重写状态机
必须改成某种设计模式
```

更好的写法：

```text
允许调整内部缓存和状态机实现，但必须保持外部协议与时序语义不变。
优先选择修改范围最小、证据最充分的方案。
```

---

## 6. 成功必须同时满足正向和负向条件

例如：

```text
正向：
- 新场景测试通过。

负向：
- 旧场景不回归；
- 不通过屏蔽错误实现；
- 不通过降低检查严格度实现；
- 不引入新的lint、CDC或时序错误。
```

只写正向条件容易出现“为了过新测试破坏旧行为”。

---

## 7. 方向发生实质变化时，清除后重建 Goal

Codex Goal 属于当前线程的持久状态，而不是全局项目记忆。若目标本身发生变化，继续通过普通消息叠加新要求，容易形成相互冲突的完成条件。更稳妥的方式是暂停或清除旧 Goal，再建立新的 Goal。

---

# 四、推荐的 Goal 模板

```text
/goal

【期望结果】
<任务完成后，系统、代码或文档应处于什么可观察状态。>

【当前事实】
- <已经确认的事实>
- <当前失败现象>
- <可复现条件>

【待验证假设】
- <线索或猜测，但不得作为既定根因>

【验收证据】
1. <检查命令、测试、benchmark、波形或生成物>
2. <通过阈值或预期结果>
3. <回归验证>

【必须保持】
- <接口、行为、性能或兼容性不变量>
- <禁止通过删除测试、硬编码等方式达成>

【工作边界】
允许修改：
- <路径或模块>

只读参考：
- <冻结基线或参考实现>

禁止修改：
- <明确的禁区>

【迭代策略】
- 先复现并建立证据基线；
- 优先执行能区分候选根因的最小实验；
- 一次只引入一个可归因变量；
- 修改后先运行最小相关测试，再运行完整回归；
- 根据证据更新假设，不重复无新证据支持的失败路径。

【阻塞与停止】
仅在所有验收证据满足时判定完成。
若环境不可用、必要信息缺失、约束冲突或无合理路径可继续，
停止修改并报告：
- 已尝试路径；
- 获得的证据；
- 当前判断及置信度；
- 未解决风险；
- 解除阻塞所需的最小输入。
```

这不一定每次都要写这么长。简单 Goal 可以压缩成一句：

```text
/goal <期望结果>，由<具体证据>验证，同时保持<约束>。
只在<边界>内工作；每轮根据最新证据选择下一项最小实验。
若无法继续，报告尝试、证据、阻塞及所需输入，不得把阻塞声明为完成。
```

# 五、自动生成高质量 Goal 的元提示词

下面这段可以交给 Codex、oh-my-pi 或其他模型。先让它生成 Goal，不直接执行。

你是 Goal Contract Architect。请把我提供的原始任务转换为一个适合 Coding Agent 持续执行的高质量 `/goal`。

Goal 不是实施计划，也不是背景摘要，而是一个可验证的完成契约。它必须让 Agent 知道：

1. 最终必须达到什么可观察状态；
2. 用什么具体证据证明完成；
3. 工作过程中哪些行为、接口和质量属性不能退化；
4. 允许读取、修改和使用哪些范围；
5. 每次迭代后如何根据新证据选择下一项行动；
6. 在什么情况下应判定阻塞并停止，而不是无限重试或虚假宣布完成。

请按以下流程处理：

第一步：判断该任务是否适合 Goal Mode。

适合条件：

- 完成条件相对明确；
- 实现路径需要根据调查或实验动态决定；
- 存在可检查的测试、日志、benchmark、生成物或其他证据。

不适合时，明确建议使用普通 Prompt、Ask Mode 或 Plan Mode，并说明原因，不要强行生成 Goal。

第二步：从原始任务中区分：

- 已确认事实；
- 用户要求；
- 暂定假设；
- 缺失但影响验收的信息。

不得把暂定假设改写成事实。只有真正阻止定义完成条件的信息才允许提出问题；其他缺失信息应使用保守、明确标注的默认假设。

第三步：生成 Goal，包含：

【期望结果】
描述完成后的系统状态，不要只描述“分析、尝试、研究、优化”等动作。

【当前事实】
仅保留与执行和验收直接相关的事实。

【待验证假设】
列出线索，但明确要求通过证据验证。

【验收证据】
每个验收项必须尽量对应具体命令、测试、日志、波形、benchmark、文件或人工检查动作。不得使用“代码质量良好”“足够健壮”等无法审计的标准。

【必须保持】
列出接口、行为、兼容性、性能、安全性和回归约束；禁止通过删除测试、降低检查严格度、硬编码测试数据或掩盖错误来达成目标。

【工作边界】
明确允许修改、只读参考和禁止修改的范围。范围要足够窄以便审计，但不能窄到阻止调查真实根因。

【迭代策略】
要求先建立基线和根因假设，优先执行信息增益最高的最小实验，一次只引入一个可归因变量，并在局部验证通过后运行完整回归。不得无新证据地重复失败路径。

【阻塞与停止】
只有验收证据全部满足时才能声明完成。若测试环境不可用、必要输入缺失、冻结约束与目标冲突或合理路径耗尽，应停止修改并报告：

- 已尝试路径；
- 证据；
- 当前最可能判断及置信度；
- 剩余风险；
- 解除阻塞所需的最小输入。

第四步：执行质量审查：

- 是否只有一个主目标；
- 是否定义了可观察的终点；
- 是否存在明确验证表面；
- 是否把假设误写成事实；
- 是否过度规定实现路径；
- 是否遗漏回归约束；
- 是否存在无限循环风险；
- 是否可能通过投机方式虚假达标。

第五步：输出以下内容：

1. 「推荐 Goal」：可以直接复制执行的完整 `/goal`；
2. 「压缩版 Goal」：适合任务上下文已经充分时使用；
3. 「待确认项」：只列真正影响完成判定的事项；
4. 「质量评分」：对可验证性、边界清晰度、路径开放度、抗投机性、停止条件分别按 0～2 分评分，并解释扣分原因。

原始任务如下：

<在这里粘贴任务、现象、相关路径、测试命令、约束和已有结论>

生成后不要立刻使用。先人工检查三个最关键的问题：**验收证据是否真的能运行、假设有没有被写成事实、成功标准是否可能被投机满足。**

# 六、结合你的项目给一个示例

## 原始需求

```text
解决板上m_axis_read_data_tlast不出现的问题。
```

## 更强的 Goal

```text
/goal

【期望结果】
找到并修复板上AXI read path无法产生m_axis_read_data_tlast的根因，
使1280×1024压缩帧读取能够完整结束且后续帧继续运行。

【当前事实】
- 仿真中read path相关回归通过；
- 板上accepted < cmd_len；
- data FIFO出现full；
- status FIFO表现为empty；
- m_axis_read_data_tlast未观察到。

【待验证假设】
status FIFO、命令长度语义、CDC或HyperRAM返回路径可能导致问题，
但不得在取得波形或实验结果前将任何一项视为既定根因。

【验收证据】
1. 现有read path和压缩链仿真回归全部PASS；
2. 板上accepted == cmd_len；
3. 每个读取命令恰好产生一次正确位置的tlast；
4. 连续读取至少10帧，无FIFO永久full/empty和状态机死锁；
5. GVSP接收端帧长度正确且bad_fcs == 0；
6. 修改前后的DDR帧布局和顶层接口一致。

【必须保持】
- 不修改冻结的DDR帧布局；
- 不改变顶层AXI Stream接口语义；
- 不通过缩短cmd_len或屏蔽错误状态规避问题；
- 不降低现有测试和断言严格度。

【工作边界】
优先调查和修改read command、read data、status及其CDC路径。
第三方AXI DMA源码作为只读基线；只有证据明确指向第三方模块时，
才报告需要扩展范围，不直接修改。

【迭代策略】
先建立板上与仿真的计数器和握手差异表。
优先执行能区分cmd_len、CDC、status返回和data backpressure的最小实验。
一次只改变一个变量；局部验证后运行完整回归。
被证据否定的假设不得无新证据重复尝试。

【阻塞与停止】
只有全部验收证据满足时才能完成。
若缺少必要板上波形、测试入口无法运行或必须修改冻结基线，
停止并报告已尝试实验、证据、当前根因排序、剩余不确定性
以及解除阻塞所需的最小输入。
```

这个版本比“修复 tlast”更高效，因为它不要求 Agent机械执行固定 Plan；更准确，因为完成由仿真和板级证据决定；更稳定，因为即使最初的 FIFO 假设错误，Goal 仍然成立。

这些原则可以直接迁移到 oh-my-pi 的 `/goal`：**把 Codex 的 Goal 当作契约设计方法，而不是特定产品的命令技巧**。OMP 的执行和预算机制可能不同，但 Outcome、Evidence、Constraints、Boundaries、Iteration、Blocked 这六部分仍然是最关键的提示词骨架。
