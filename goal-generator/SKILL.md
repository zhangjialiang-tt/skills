# Goal Generator

把原始任务转换为适合 Coding Agent 持续执行的高质量 `/goal` 完成契约。

## 什么时候该用，什么时候不该用

**适合 → 生成 Goal：**
- 完成条件相对明确
- 实现路径需要根据调查或实验动态决定
- 存在可检查的测试、日志、benchmark、生成物或其他证据

**不适合 → 建议其他模式：**
- 一次性修改、纯探索、尚未确定方向的架构讨论 → 普通 Prompt 或 Plan Mode
- 任务模糊到无法定义任何完成条件 → 先 Plan

## 核心契约：六部分 + 质量门禁

每个 Goal 必须包含以下六部分。简单任务可以压缩，但逻辑上不能缺失任何一项。

```
/goal

【期望结果】完成后系统是什么样（可观察状态，不是动作）
【当前事实】已经确认的现象/测试/日志
【待验证假设】线索/猜测，但不得作为既定根因
【验收证据】每项 = 具体命令/条件 + 通过阈值（必须可执行）
【必须保持】可验证的不变量 + 反投机约束
【工作边界】允许修改 / 只读参考 / 禁止修改
【迭代策略】基线 → 最小实验 → 单变量 → 局部验证 → 完整回归
【阻塞与停止】≥3 种阻塞情形 + 阻塞时必须报告的内容
```

### 质量门禁（生成后自检，全部通过才能输出）

| # | 检查项 | 失败时修正 |
|---|--------|-----------|
| 1 | 六部分齐全 | 补缺失章节 |
| 2 | Outcome 不含动作词（分析/研究/尝试/优化/实现/改造） | 改写为可观察状态描述 |
| 3 | 每项验收证据包含具体命令/条件 + 数值阈值 | 补命令名和通过标准 |
| 4 | Constraints 包含至少一项反投机约束 | 添加"不通过删除测试/硬编码/屏蔽错误来虚假达标" |
| 5 | Blocked 列出 ≥3 种具体阻塞情形 | 补充环境/输入/约束冲突等场景 |
| 6 | 用户提供的指标（如"每周 3-5 例"）在验收证据中有目标阈值 | 添加量化通过标准 |
| 7 | 假设与事实严格分离（参见下方） | 将假设移至【待验证假设】 |

## 关键规则 1：事实 vs 假设分离

**这是无 skill 模型最容易出错的地方。**

| 用户说的 | 属于 | 写入位置 |
|---------|------|---------|
| "仿真回归能通过" | 已确认事实 | 【当前事实】 |
| "data FIFO 出现 full" | 已确认事实 | 【当前事实】 |
| "可能是 status FIFO 导致" | 暂定假设 | 【待验证假设】 |
| "我觉得应该加个幂等锁" | 用户建议 | 【待验证假设】 |
| "因为网络超时导致重试" | 归因假设 | 【待验证假设】 |

**必须避免：**
- ❌ 把"可能是 status FIFO 导致"写成"根因是 status FIFO"
- ❌ 把"需要提高性能"写成具体的优化手段（如"增加三级 FIFO"）
- ❌ 把"不能破坏接口"写成模糊的"保持接口优雅"

## 关键规则 2：验收证据必须可执行

每项验收证据必须包含两个要素：
1. **检查动作**：具体的命令、脚本名、测试路径
2. **通过阈值**：明确的数值或可观察条件

```
❌ 模糊："测试通过"、"功能正确"、"代码质量良好"
✅ 可执行："pytest tests/test_payment.py -v 全部 PASS"
✅ 可执行："benchmarks/payment_bench.py P99 < 10ms"
✅ 可执行："重复扣款发生率 < 1 例/周（当前 3-5 例/周）"
```
### 关键规则 4：用户提供的指标必须转化为验收阈值

**如果用户提到了具体数字（如"每周 3-5 例"、"延迟 X ms"、"N GB"、"8 fps"），验收证据中必须包含该指标的目标阈值，且必须基于用户数字推导。**

```
❌ 错误：用户说"每周 3-5 例" → 验收写"零重复扣款"（绝对化，无法验证渐进改善）
✅ 正确：用户说"每周 3-5 例" → 验收写"重复扣款 < 1 例/周（较当前降低 80%）"

❌ 错误：用户说"好几秒" → 验收写"搜索变快了"
✅ 正确：用户说"好几秒" → 验收写"P95 < 500ms（当前约 2-3s）"
```

### 关键规则 5：反投机约束必须领域具体

**不能只写"不通过删除测试来虚假达标"这种泛泛之谈。必须根据任务领域写出具体的投机手段。**

| 领域 | 具体反投机约束 |
|------|---------------|
| 支付/金融 | 不通过拒绝所有重复请求来达成"零重复扣款"；不通过合并多笔交易规避逐笔对账 |
| 性能优化 | 不通过减少返回结果数量、降低采样率、关闭核心功能来虚标性能提升 |
| 硬件/嵌入式 | 不通过降频、关闭校验模块、缩短测试时长来通过可靠性测试 |
| 搜索/推荐 | 不通过只返回热门结果、降低结果多样性来优化延迟或相关性指标 |
| 测试覆盖率 | 不通过删除边界条件测试、mock 外部依赖、写无意义断言来提高覆盖率 |

### 关键规则 6：迭代策略必须以可执行的复现为第一步

**"先复现"不是"先分析"。第一步必须包含可执行的操作（命令、脚本、场景），让人能稳定触发问题。**

```
❌ 错误："1. 分析现有日志，确认重复扣款的具体模式和根因"
✅ 正确："1. 在测试环境模拟网络超时（tc qdisc 注入延迟），触发客户端自动重试，确认至少复现 1 次重复扣款场景"

❌ 错误："1. 使用 ILA 抓取波形"
✅ 正确："1. 在 tb/read_path/tb_read_path_fifo_run.sv 中启动回归，连续运行 10 帧，确认 status FIFO empty 信号在 accepted < cmd_len 时被观察到"
```


**如果用户提到了一个指标（如"每周 3-5 例"、"延迟太慢"、"好几秒"），验收证据中必须包含该指标的目标阈值。**

## 关键规则 3：反投机约束必须显式

每个 Goal 的【必须保持】部分必须至少包含一条反投机约束：

```
- 不通过删除测试、硬编码数据、屏蔽错误日志、降低断言严格度来虚假达标
- 不通过缩短测试范围来规避问题
```

## 关键规则 4：阻塞条件必须具体

不要写"继续直到完成"。明确列出 ≥3 种阻塞情形：

```
- 必要测试环境无法运行
- 缺少输入数据、硬件或授权
- 冻结接口与验收目标存在直接冲突
- 所有合理路径均已被证据否定
- 继续推进必须修改当前禁止修改的范围
```

## 生成流程

### 第一步：判断适合性
参见"什么时候该用"部分。不适合则建议其他模式，不要强行生成。

### 第二步：提取与分类
从用户输入中提取：
- **事实**：有证据支持的现象
- **要求**：用户明确的目标
- **假设**：线索/猜测/建议
- **缺失信息**：影响验收但尚未获得的内容

### 第三步：生成六部分
按核心契约结构生成，每个验收项包含命令+阈值。

### 第四步：质量自检
逐项检查上述 7 条质量门禁。

### 第五步：输出
按模板输出完整 Goal + 压缩版 + 待确认项 + 质量评分。

## 输出模板

```
/goal

【期望结果】
<任务完成后，系统、代码或文档应处于什么可观察状态。禁止出现"分析/研究/尝试/优化/实现/改造"等动作词。>

【当前事实】
- <已经确认的事实，有证据支持>
- <当前失败现象>
- <可复现条件>

【待验证假设】
- <线索或猜测，但不得作为既定根因。用"可能"、"待验证"等措辞。>

【验收证据】
1. <检查命令/脚本/测试>，通过阈值：<数值或可观察条件>
2. <检查命令/脚本/测试>，通过阈值：<数值或可观察条件>
3. <回归验证命令>，通过阈值：<原有测试全部 PASS>

【必须保持】
- <接口、行为、性能或兼容性不变量>
- <反投机约束：不通过删除测试/硬编码/屏蔽错误来虚假达成>

【工作边界】
允许修改：
- <路径或模块>

只读参考：
- <冻结基线或参考实现>

禁止修改：
- <明确的禁区>

【迭代策略】
- 先复现并建立证据基线；
- 优先执行能区分候选根因的最小实验；
- 一次只引入一个可归因变量；
- 修改后先运行最小相关测试，再运行完整回归；
- 根据证据更新假设，不重复无新证据支持的失败路径。

【阻塞与停止】
仅在所有验收证据满足时判定完成。
若环境不可用、必要信息缺失、约束冲突或无合理路径可继续，
停止修改并报告：
- 已尝试路径；
- 获得的证据；
- 当前判断及置信度；
- 未解决风险；
- 解除阻塞所需的最小输入。
```

## 实战技巧

- 一个 Goal 只维护一个主完成条件
- 模糊任务先 Plan，再 Goal
- 不要把完整 Plan 复制成 Goal（Plan 描述路线，Goal 描述完成契约）
- 优先使用行为标准，不要指定实现细节
- 方向发生实质变化时，清除后重建 Goal
