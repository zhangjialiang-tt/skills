# Diagnostic Goal 示例

本文档收录真实场景下的 Diagnostic Goal 示例。每个示例都包含**输入**和**可直接复制的输出**。

---

## 示例 1：Bug 定位（用户提供未验证猜测）

**输入：** "我们的支付系统最近偶尔会出现重复扣款的问题。客服说是因为网络超时导致客户端重试引起的，我觉得应该加个幂等锁。重复扣款的报告大约有每周 3-5 例，主要是移动端用户。测试可以用 pytest tests/test_payment.py，基准在 benchmarks/payment_bench.py。数据库是 PostgreSQL 14，后端是 Python/FastAPI。"

**输出：**

```text
/goal

【期望结果】
消除支付系统的重复扣款问题，使其发生率降至可接受水平，同时保持现有支付 API 和用户体验不变。

【当前事实】
- 支付系统偶尔出现重复扣款
- 重复扣款报告约每周 3-5 例
- 主要影响移动端用户
- 测试入口：pytest tests/test_payment.py
- 基准：benchmarks/payment_bench.py
- 数据库：PostgreSQL 14
- 后端：Python/FastAPI

【待验证假设】
- 客服归因于网络超时导致客户端自动重试（待验证）
- 用户建议加幂等锁（待验证方案）
- 可能存在的其他根因：数据库唯一约束缺失、并发控制不当、消息队列重复投递

【验收证据】
1. pytest tests/test_payment.py -v 全部 PASS（回归验证）
2. benchmarks/payment_bench.py 报告 P99 延迟不高于当前基准（性能不退化）
3. 重复扣款发生率目标：先基于生产日志建立可靠基线并读取现有 SLO；当前 3-5 例/周仅为现状（baseline），非目标；若无可复用 SLO，基于真实基线与业务可接受度提出 2-3 个候选目标（含成本/范围影响）供用户确认后写入。
4. 模拟网络超时场景下，同一笔订单不会产生多次扣款（复现场景验证）
5. 修改前后支付 API 请求/响应格式一致（接口一致性检查）

【必须保持】
- 不改变现有支付 API 的请求/响应格式
- 不降低现有测试覆盖率
- 不通过拒绝所有重复请求来达成"零重复扣款"
- 不通过合并多笔交易规避逐笔对账
- 不屏蔽重试错误日志来虚假达标
- 不修改数据库 schema（除非用户明确授权）

【工作边界】
允许修改：
- services/payment/ 目录内的业务逻辑
- tests/test_payment.py 中的测试用例
- benchmarks/payment_bench.py 中的基准测试

只读参考：
- 第三方支付提供商 SDK 源码
- 数据库 schema 定义

禁止修改：
- 生产数据库配置
- 第三方支付提供商 SDK 源码
- 用户明确冻结的接口或协议

【迭代策略】
1. 在测试环境模拟网络超时（tc qdisc 注入延迟），触发客户端自动重试，确认至少复现 1 次重复扣款场景
2. 建立当前重复扣款的日志模式基线（时间分布、用户特征、金额分布）
3. 优先执行能区分"网络超时重试"与"其他根因"的最小实验
4. 一次只引入一个可归因变量（如添加幂等键）
5. 修改后先运行 tests/test_payment.py，再运行完整回归
6. 根据证据更新假设，不重复无新证据支持的失败路径

【阻塞与停止】
仅在所有验收证据满足时判定完成。
若测试环境无法模拟网络超时、缺少生产日志访问权限、或必须修改数据库 schema，
停止并报告：
- 已尝试路径
- 每条路径的证据
- 当前最可能根因及置信度
- 尚未验证的假设
- 阻塞原因
- 解除阻塞所需的最小输入
```

> **注意：** 用户给出的 3-5 例/周 是当前状态（baseline），不是目标，只写入【当前事实】。验收目标不编造具体数字（如 <1 例/周），而是先建立可靠基线、读取现有 SLO，再提出候选目标由用户确认后写入。这避免了 Skill 静默把 baseline 转换为目标或替用户决定验收标准。若目标待用户确认，Goal 应分两阶段：阶段一完成基线测量并提交候选目标后暂停，用户批准前不进入实现、不宣布整个 Goal 完成（见 SKILL 规则 3 阶段门）。

## 示例 2：FPGA/RTL 调试

**输入：** "解决板上 m_axis_read_data_tlast 不出现的问题。目前仿真回归能通过，但板上 accepted < cmd_len，观察到 data FIFO 出现 full，status FIFO 表现为 empty，tlast 完全没有出现。可以修改 rtl/read_path/**、tb/read_path/**、scripts/run_read_regression.py，不能动第三方 AXI DMA 源码和帧格式。"

**输出：**

```text
/goal

【期望结果】
找到并修复板上 AXI read path 无法产生 m_axis_read_data_tlast 的根因，使 1280×1024 压缩帧读取能够完整结束且后续帧继续运行。

【当前事实】
- 仿真中 read path 相关回归通过
- 板上 accepted < cmd_len
- data FIFO 出现 full
- status FIFO 表现为 empty
- m_axis_read_data_tlast 未观察到

【待验证假设】
- status FIFO empty 可能是根因，但不得在取得波形或实验结果前视为既定根因
- 命令长度语义、CDC 或 HyperRAM 返回路径也可能导致问题
- data FIFO full 可能是 status FIFO empty 的结果而非原因

【验收证据】
1. 现有 read path 和压缩链仿真回归全部 PASS
2. 板上 accepted == cmd_len
3. 每个读取命令恰好产生一次正确位置的 tlast
4. 连续读取至少 10 帧，无 FIFO 永久 full/empty 和状态机死锁
5. GVSP 接收端帧长度正确且 bad_fcs == 0
6. 修改前后的 DDR 帧布局和顶层接口一致

【必须保持】
- 不修改冻结的 DDR 帧布局
- 不改变顶层 AXI Stream 接口语义
- 不通过缩短 cmd_len 或屏蔽错误状态规避问题
- 不降低现有测试和断言严格度
- 不修改第三方 AXI DMA 源码

【工作边界】
优先调查和修改 read command、read data、status 及其 CDC 路径。
第三方 AXI DMA 源码作为只读基线；只有证据明确指向第三方模块时，
才报告需要扩展范围，不直接修改。

【迭代策略】
1. 在 tb/read_path/tb_read_path_fifo_run.sv 中启动回归，连续运行 10 帧，确认 status FIFO empty 信号在 accepted < cmd_len 时被观察到
2. 建立板上与仿真的计数器和握手差异表
3. 优先执行能区分 cmd_len、CDC、status 返回和 data backpressure 的最小实验
4. 一次只改变一个变量；局部验证后运行完整回归
5. 被证据否定的假设不得无新证据重复尝试

【阻塞与停止】
只有全部验收证据满足时才能完成。
若缺少必要板上波形、测试入口无法运行或必须修改冻结基线，
停止并报告已尝试实验、证据、当前根因排序、剩余不确定性
以及解除阻塞所需的最小输入。
```

## 示例 3：性能优化

**输入：** "我们的文档搜索功能太慢了，用户抱怨加载要等好几秒。我们用的是 Elasticsearch 8.x，索引大概有 200GB。搜索接口 GET /api/search?q=... 目前用的是 match 查询，返回前 100 条。"

**输出：**

```text
/goal

【期望结果】
将文档搜索接口的响应时间降低到可接受水平，同时保持搜索结果的相关性和完整性不退化。具体目标需基于当前基线测量后由用户确认。

【当前事实】
- 搜索接口 GET /api/search?q=... 响应时间用户反馈"好几秒"（待测量确认）
- 使用 Elasticsearch 8.x，索引约 200GB
- 当前使用 match 查询，返回前 100 条
- 搜索服务代码在 services/search.py
- 测试在 tests/test_search.py

【待验证假设】
- 慢查询可能源于 match 查询的全文扫描
- 返回 100 条结果可能过多
- 索引结构可能未针对当前查询模式优化
- 可能存在 N+1 查询或重复检索问题

【验收证据】
1. tests/test_search.py 全部 PASS（回归验证）
2. 搜索接口响应时间目标：先测量当前 P50/P95/P99 基线并读取现有 SLO/体验要求；若无可复用目标，基于真实基线提出 2-3 个候选（含对成本/范围影响）供用户确认后写入。
3. 搜索结果与当前实现相比，Top-10 召回率不低于基线水平（相关性不退化）
4. 稳定性验证：连续多次搜索无超时或错误
5. 返回结果数量可配置，默认保持 100 条（功能一致性）

【必须保持】
- 不改变搜索 API 的请求/响应格式
- 不降低搜索结果相关性（通过召回率验证）
- 不通过减少返回结果数量来虚假提速
- 不通过降低采样率或关闭核心功能来虚标性能提升
- 不修改 Elasticsearch 集群配置（除非用户明确授权）

【工作边界】
允许修改：
- services/search.py 中的查询逻辑
- tests/test_search.py 中的测试用例
- 应用层缓存和查询优化

只读参考：
- Elasticsearch 索引 mapping 和 settings
- 现有搜索相关性测试数据

禁止修改：
- Elasticsearch 集群配置
- 索引 mapping（除非用户明确授权）
- 其他服务的代码

【迭代策略】
1. 先建立当前搜索性能的基准（P50/P95/P99、查询类型分布）
2. 分析慢查询日志，定位瓶颈（查询解析、网络延迟、结果排序）
3. 优先执行能区分"查询本身慢"与"结果处理慢"的最小实验
4. 一次只引入一个优化（如添加缓存、调整查询类型、减少返回字段）
5. 每次优化后运行 tests/test_search.py 和性能基准
6. 被证据否定的优化路径不重复尝试

【阻塞与停止】
仅在所有验收证据满足时判定完成。
若 ES 配置无法修改、相关性无法客观衡量、或索引结构不可变，
停止并报告已尝试路径、证据、当前瓶颈分析、剩余优化空间
以及解除阻塞所需的最小输入。
```

> **注意：** 用户反馈"好几秒"被标注为"待测量确认"，而非改写为 2-3 秒。验收目标不编造具体数字（如 P95 < 500ms），而是先测量真实基线、读取 SLO/体验要求，再提出候选目标由用户确认后写入。这避免了 Skill 替用户决定验收标准。若目标待用户确认，Goal 应分两阶段：阶段一完成基线测量并提交候选目标后暂停，用户批准前不进入实现、不宣布整个 Goal 完成（见 SKILL 规则 3 阶段门）。

## 示例 4：数据一致性问题

**输入：** "用户反馈购物车里的商品数量偶尔会不对，可能是并发问题。"

**输出：**

```text
/goal

【期望结果】
消除购物车商品数量不一致的问题，确保在高并发场景下购物车数据准确，同时保持现有用户体验和接口响应性能。

【当前事实】
- 用户反馈购物车商品数量偶尔不对
- 怀疑是并发问题（待验证）

【待验证假设】
- 并发更新导致丢失更新（lost update）
- 数据库隔离级别不当
- 应用层缺少乐观锁或悲观锁
- 缓存与数据库不一致

【验收证据】
1. 并发测试：模拟同时更新购物车场景，最终数量正确
2. 现有购物车相关测试全部 PASS
3. 接口响应时间 P95 不高于当前基准（性能不退化）
4. 模拟网络重试场景下，同一操作不会导致数量重复增加

【必须保持】
- 不改变购物车 API 的请求/响应格式
- 不降低现有测试覆盖率
- 不通过锁定整个用户表来规避并发问题
- 不屏蔽错误日志来虚假达标

【工作边界】
允许修改：
- 购物车服务层代码
- 数据库访问层（ORM 查询）
- 相关测试代码

只读参考：
- 数据库 schema
- 缓存配置

禁止修改：
- 数据库 schema（除非用户明确授权）
- 其他服务的代码

【迭代策略】
1. 先复现：模拟并发更新购物车，确认至少 1 次数量不一致
2. 分析当前数据库隔离级别和更新语句
3. 优先执行能区分"并发写入"与"缓存不一致"的最小实验
4. 一次只引入一种并发控制手段（如乐观锁版本号）
5. 修改后先运行并发测试，再运行完整回归

【阻塞与停止】
仅在所有验收证据满足时判定完成。
若无法复现并发问题、缺少数据库写权限、或必须修改 schema，
停止并报告已尝试路径、证据、当前判断及所需输入。
```

> **注意：** 此示例中用户未提供任何指标，因此验收证据不包含具体数值目标。Skill 不应编造"100 个同时请求"或"P95 < X ms"等数字，除非用户明确要求或提供了可推导的基线。
