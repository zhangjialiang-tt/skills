# Common Failure Modes

## 失败模式 1：把假设写成事实

**错误示例：**
```
/goal 修复由于 status FIFO 丢失导致的 tlast 问题
```

**正确示例：**
```
/goal 找到并修复导致板上 read path 无法产生 tlast 的根因。
当前线索是 status FIFO empty，但不得将其视为既定根因，
必须通过波形、计数器或最小实验验证。
```

**错误示例：**
```
/goal 修复由于网络超时导致的重复扣款问题
```

**正确示例：**
```
/goal 消除支付系统的重复扣款问题，使其发生率降至可接受水平。
当前客服归因于网络超时导致重试，但必须在取得日志或实验结果后，
才能确认根因。
```

## 失败模式 2：验收证据模糊

**错误示例：**
```
- 测试通过
- 功能正确
- 代码质量良好
- 系统稳定运行
```

**正确示例：**
```
- pytest tests/test_payment.py -v 全部 PASS
- benchmarks/payment_bench.py 报告 P99 < 10ms
- 重复扣款发生率 < 1 例/周（当前 3-5 例/周）
- ILA 采样显示每个读取命令恰好产生一次 tlast
```

## 失败模式 3：缺少反投机约束

**错误示例：**
```
【必须保持】
- 保持现有回归通过
- 不修改公共 API
```

**正确示例：**
```
【必须保持】
- 保持现有回归通过
- 不修改公共 API
- 不通过删除测试、硬编码数据、屏蔽错误日志、降低断言严格度来虚假达标
- 不通过缩短 cmd_len 或屏蔽错误状态规避问题
```

## 失败模式 4：Outcome 描述动作而非状态

**错误示例：**
```
【期望结果】
- 优化压缩模块
- 实现异步写入
- 重构代码结构
- 加个幂等锁
```

**正确示例：**
```
【期望结果】
- 压缩模块稳定支持 1280×1024@50Hz 输入
- 日志模块完成异步改造并稳定运行
- 支付系统重复扣款率 < 1 例/周
- 文档搜索 P95 < 500ms
```

## 失败模式 5：缺少 Blocked 条件

**错误示例：**
```
【阻塞与停止】
继续直到完成
```

**正确示例：**
```
【阻塞与停止】
以下情况视为阻塞，不得宣布完成：
- 必要测试环境无法运行
- 缺少输入数据、硬件或授权
- 冻结接口与验收目标存在直接冲突
- 所有合理路径均已被证据否定
- 继续推进必须修改当前禁止修改的范围

阻塞时停止并报告：
1. 已尝试路径
2. 每条路径的证据
3. 当前最可能根因
4. 尚未验证的假设
5. 阻塞原因
6. 解除阻塞所需的最小输入
```

## 失败模式 6：用户指标未转化为验收阈值

**错误示例：**
用户说："重复扣款每周 3-5 例"

Goal 验收证据中：
```
- 重复扣款问题解决
- 测试通过
```

**正确示例：**
```
- 重复扣款发生率 < 1 例/周（当前 3-5 例/周，降低 80% 以上）
```

**触发条件：** 只要用户提供了具体数字（如"每周 N 例"、"延迟 X ms"、"N GB"），验收证据必须包含该指标的目标阈值。
