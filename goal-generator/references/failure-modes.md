# Common Failure Modes

本文档收录真实的 Goal 生成失败案例及其修正版本。每个失败模式都包含**错误示例**、**正确示例**和**触发条件**。

---

## 失败模式 1：把假设写成事实（Diagnostic）

**错误示例：**
```
/goal 修复由于 status FIFO 丢失导致的 tlast 问题
```

**正确示例：**
```
/goal 找到并修复导致板上 read path 无法产生 tlast 的根因。
当前线索是 status FIFO empty，但不得将其视为既定根因，
必须通过波形、计数器或最小实验验证。
```

**触发条件：** 用户提出未验证的根因猜测时，必须写入【待验证假设】而非【当前事实】。

---

## 失败模式 2：验收证据模糊

**错误示例：**
```
- 测试通过
- 功能正确
- 代码质量良好
- 系统稳定运行
```

**正确示例：**
```
- pytest tests/test_payment.py -v 全部 PASS
- benchmarks/payment_bench.py 报告 P99 < 10ms
- 重复扣款发生率 < 1 例/周（用户目标，当前 baseline 3-5 例/周）
- ILA 采样显示每个读取命令恰好产生一次 tlast
```

**触发条件：** 验收证据必须包含具体检查动作 + 通过阈值。

---

## 失败模式 3：缺少反投机约束

**错误示例：**
```
【必须保持】
- 保持现有回归通过
- 不修改公共 API
```

**正确示例：**
```
【必须保持】
- 保持现有回归通过
- 不修改公共 API
- 不通过删除测试、硬编码数据、屏蔽错误日志、降低断言严格度来虚假达标
- 不通过缩短 cmd_len 或屏蔽错误状态规避问题
```

**触发条件：** 存在可投机的代理/性能/覆盖率/可靠性指标，或删除/迁移等可投机场景时，Constraints 必须包含至少一项领域相关的反投机约束；纯不变量（如"不修改公共 API"）不能替代反投机约束。非 gameable 任务只需不变量。

---

## 失败模式 4：Outcome 描述动作而非状态

**错误示例：**
```
【期望结果】
- 优化压缩模块
- 实现异步写入
- 重构代码结构
- 加个幂等锁
```

**正确示例：**
```
【期望结果】
- 压缩模块稳定支持 1280×1024@50Hz 输入
- 日志模块完成异步改造并稳定运行
- 支付系统重复扣款率 < 1 例/周（用户目标）
- 文档搜索 P95 < X ms（待基线测量后确认）
```

**触发条件：** Outcome 必须描述完成后的可观察状态。

---

## 失败模式 5：缺少 Blocked 条件

**错误示例：**
```
【阻塞与停止】
继续直到完成
```

**正确示例：**
```
【阻塞与停止】
以下情况视为阻塞，不得宣布完成：
- 必要测试环境无法运行
- 缺少输入数据、硬件或授权
- 冻结接口与验收目标存在直接冲突
- 所有合理路径均已被证据否定
- 继续推进必须修改当前禁止修改的范围

阻塞时停止并报告：
1. 已尝试路径
2. 每条路径的证据
3. 当前最可能根因
4. 尚未验证的假设
5. 阻塞原因
6. 解除阻塞所需的最小输入
```

**触发条件：** Diagnostic Goal 必须列出 ≥3 种阻塞情形 + 报告内容。

---

## 失败模式 6：用户目标指标被丢弃（confirmed target 未进入验收）

**错误示例：**
用户明确说："重复扣款必须降到每周 1 例以下"

Goal 验收证据中：
```
- 重复扣款问题解决
- 测试通过
```

**正确示例：**
```
- 重复扣款发生率 < 1 例/周（用户明确目标）
```

**触发条件：** 用户明确给出目标指标（confirmed target，如"降到 X 以下""不超过 Y"）时，必须进入验收阈值。注意：用户只描述当前状态（baseline，如"目前每周 3-5 例"）时不适用本条——baseline 不得转换为目标，见失败模式 7。

---

## 失败模式 7：baseline 静默转换为目标（新增）

**错误示例：**
用户说："搜索好几秒"

Goal 验收证据中：
```
- 搜索接口 P95 响应时间 < 500ms（当前约 2-3s）
```

**正确示例：**
```
- 搜索接口响应时间目标：先测量当前 P50/P95/P99 基线并读取现有 SLO；若无可复用目标，基于真实基线提出 2-3 个候选供用户确认后写入
```

**触发条件：** 用户描述当前状态（baseline）时，只能写入 Current Facts，不得自动推导为目标。

---

## 失败模式 8：Profile 误选

**错误场景：** 用户说"帮我做一个简单的桌面工具"，但 Agent 生成了完整的 Diagnostic Goal 包含事实/假设/复现。

**错误做法：** 对简单产品任务使用 Diagnostic Profile。

**正确做法：** 识别为 Standard Goal，使用默认策略快速推进。

---

## 失败模式 9：迭代策略以"分析"为第一步

**错误示例：**
```
1. 分析现有日志，确认重复扣款的具体模式和根因
```

**正确示例：**
```
1. 在测试环境模拟网络超时（tc qdisc 注入延迟），触发客户端自动重试，确认至少复现 1 次重复扣款场景
```

**原因：** "先分析"是不可执行的操作。第一步必须包含具体的命令、脚本或场景。

---

## 失败模式 10：反投机约束泛泛

**错误示例：**
```
- 不通过删除测试来虚假达标
```

**正确示例（性能优化领域）：**
```
- 不通过减少返回结果数量、降低采样率、关闭核心功能来虚标性能提升
```

**原因：** 泛泛的约束无法审计，必须按领域写出具体的投机手段。

---

## 失败模式 11：跨领域示例污染（新增）

**错误示例：** 支付示例的【工作边界】中出现"第三方 AXI DMA 源码"和"已冻结的帧格式"。

**正确做法：** 支付示例只涉及支付相关领域（PostgreSQL、支付 SDK、幂等锁等），不应混入 FPGA/RTL 领域实体。

**原因：** 参考示例会直接影响模型输出。跨领域污染会导致模型在支付任务中错误地加入 FPGA 约束。

**检测方法：** 支付任务不得出现 FPGA、AXI、帧格式；RTL 任务不得出现 PostgreSQL、支付 SDK；文档任务不得出现与输入无关的生产数据库规则。

---

## 失败模式 12：trigger 过宽（新增）

**错误场景：** 用户说"修复 tlast 不出现的问题"，没有明确要求生成 Goal，但 Skill 自动生成了 Goal。

**错误做法：** 把弱信号（"修复""根因""优化"）当作强触发词。

**正确做法：** 弱信号只能用于 Profile 判断，不能单独触发。用户没有明确要求生成 Goal 时，应该直接调试。

**原因：** 过宽的触发会导致 Skill 抢占 Plan 或直接执行任务。

---

## 失败模式 13：多目标混合未拆分（新增）

**错误示例：**
```
/goal 删除所有测试用户的订单数据，然后优化一下查询速度
```

**正确做法：** 拆分为两个 Goal：
- Goal A：安全清理测试订单数据（破坏性任务，需先确认范围、备份、授权）
- Goal B：建立基准并优化查询性能（非破坏性，可独立执行）

**原因：** 一个 Goal 只能有一个主完成结果。多个目标如果拥有不同风险、验证方式或修改边界，应拆分成多个 Goal。
