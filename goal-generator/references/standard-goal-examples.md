# Standard Goal 示例

本文档收录真实场景下的 Standard Goal 示例。

---

## 示例 1：新产品原型（模糊需求）

**输入：** "帮我做一个简单的桌面工具"

**输出：**

```text
推荐执行版（中文，可直接复制）
/goal 创建一个第一版本地桌面工具 MVP，先读取工作区内的项目文档和可用脚本，实现核心用户可见流程，并避免改动无关系统。
验证：运行项目提供的最小相关检查，启动本地应用或对应运行环境，完整走通一次核心流程，并用日志、截图或命令输出作为证据。
约束：不加入账号、付费服务、生产变更、破坏性操作或无关功能，除非用户明确要求。
边界：只写入新项目目录，或只修改现有项目中与该功能直接相关的文件。
迭代策略：一次实现一个聚焦工作流，每次有意义改动后重跑检查，重试前先读日志，最多做 3 轮聚焦改进后报告剩余风险。
完成条件：核心流程有运行证据证明可用，检查通过或明确说明缺少配置。
暂停条件：需要凭证、付费、生产数据、破坏性操作、法律/医疗/金融判断、版权素材或所有权不清时暂停。

默认选择理由：先做本地 MVP，因为它能最快验证核心体验，同时避免账号、后端和发布流程拖慢第一版。

可选调整
1. 项目形态：A 新建本地 MVP（默认） / B 改现有项目 / C 先做可交互原型
2. 范围：A 核心流程（默认） / B 加常见增强 / C 做完整产品
3. 验证：A 本地运行检查（默认） / B 真机或线上检查 / C 发布前检查

你可以直接回复：按默认，或回复类似 1B 2A 3C。
```

## 示例 2：文档任务（不适合数值化）

**输入：** "帮我写一份 API 文档，涵盖用户认证模块"

**输出：**

```text
/goal 创建用户认证模块的 API 文档，覆盖所有公开端点、请求/响应格式、错误码和示例。
验证：
1. 文档包含所有 /auth 端点的说明（枚举检查）
2. 每个端点有完整的请求参数表和响应示例（结构检查）
3. 文档格式符合项目现有文档风格（对比检查）
4. 至少 3 个核心端点有完整的 curl 示例且可实际运行（执行检查）
约束：不改变任何代码实现；不修改现有接口行为；文档风格与项目现有文档保持一致。
边界：只写入 docs/ 目录或用户指定的文档路径；不修改 src/ 或 tests/ 中的代码。
迭代策略：先完成核心端点文档，再补充边缘场景；每完成一个章节后对比现有文档风格。
完成条件：所有公开端点有完整文档，示例可运行，格式一致。
暂停条件：需要访问生产环境用户数据、修改代码实现、或涉及未公开的私有 API 时暂停。
```

> **注意：** 文档任务不使用数值阈值，而是使用结构检查、枚举检查和执行检查。这比强制 P95 < X 更合理。

## 示例 3：UI 修改

**输入：** "把登录页改成更现代的风格"

**输出：**

```text
/goal 更新登录页视觉风格，使其更现代、专业，同时保持现有交互功能和可访问性。
验证：
1. 运行前端检查（lint/typecheck）通过
2. 桌面和移动端截图对比显示视觉层级、间距、字体、可读性改善
3. 核心登录流程端到端测试通过（输入账号密码 → 登录成功）
4. 可访问性检查（键盘导航、屏幕阅读器标签）通过
约束：不改变登录交互流程；不修改后端认证接口；不删除现有功能；不引入新的 UI 依赖（除非用户明确要求）。
边界：只修改登录页相关组件、样式和直接相关测试；不修改共享布局组件或全局样式系统。
迭代策略：基于截图做最多 3 轮聚焦视觉改进，优先调整层级、间距、字体、控件密度；每轮对比前后截图。
完成条件：前端检查通过，截图显示视觉改善，登录流程测试通过，可访问性不退化。
暂停条件：需要修改品牌设计系统、引入新的 UI 库、改变交互流程或涉及多页面重构时暂停。
```

## 示例 4：常规重构（有明确完成边界）

**输入：** "把 utils/ 目录下的重复代码合并一下"

**输出：**

```text
/goal 合并 utils/ 目录下的重复代码，提取公共逻辑到独立模块，消除重复，同时保持所有现有调用点行为不变。
验证：
1. 现有测试套件全部 PASS（回归验证）
2. 重复代码行数减少（可通过静态分析工具测量）
3. 公共模块有清晰的接口文档和至少 3 个调用点（结构检查）
4. 无新增 lint 警告或类型错误（静态检查）
约束：不改变任何公共函数签名（除非所有调用点同步更新）；不修改函数外部行为；不降低现有测试覆盖率。
边界：只修改 utils/ 目录内的文件；不修改调用 utils/ 的上层模块（除非必要且同步更新）。
迭代策略：每次提取一个公共函数，运行相关测试，确认无回归后再进行下一次提取。
完成条件：测试全部通过，重复代码显著减少，公共模块接口清晰。
暂停条件：需要修改公共 API 签名、改变外部行为、或涉及跨目录重构时暂停。
```

## 示例 5：多目标混合（应拆分）

**输入：** "帮我删库里所有测试用户的订单数据，然后优化一下查询速度"

**输出：**

```text
⚠️ 此任务包含两个不同目标，建议拆分为两个 Goal：

/goad A：安全清理测试订单数据
目标：识别并安全删除明确范围内的测试订单数据
验证：确认数据范围、备份完成、删除命令执行成功、行数核对
约束：不删除生产用户数据；不修改表结构；必须有备份
边界：只操作测试环境数据库；不影响生产环境
暂停条件：需要确认数据范围、备份策略、授权

/goal B：优化查询性能
目标：建立当前查询性能基准，识别瓶颈，优化查询速度
验证：对比优化前后查询延迟（P95/P99）；索引使用分析
约束：不修改表结构（除非用户明确授权）；不改变查询结果
边界：只修改查询语句和索引；不修改业务逻辑
暂停条件：需要修改表结构、修改业务逻辑、或生产环境变更时暂停

建议先执行 Goal A（破坏性任务优先确认），再执行 Goal B（性能优化）。
```

> **注意：** 此示例展示了"单一主结果"门禁的应用——Skill 检测到多个目标时主动拆分，而不是混成一个 Goal。
